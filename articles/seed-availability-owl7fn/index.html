节点被墙如何解决：先确认，再处理

节点“被墙”没有一次性解决办法。可行的顺序是：先确认真实原因，再按层处理，最后调整架构。对机场运营者来说，常见现象有三种：国内用户大面积超时但海外测试正常；同一节点在部分省份或运营商下不可用；换 IP 后恢复几天到几周，随后再次失效。前两种不一定是封锁，也可能是线路拥塞、配置错误或证书问题。第三种通常说明入口暴露后又被识别。

建议先做三件事。第一，在国内和海外分别测试同一节点，确认问题是否只出现在国内方向。第二，判断故障停在 IP、端口还是 TLS 层。第三，检查服务端进程、证书和客户端配置是否一致。确认是 IP 或端口被封后，短期可以更换入口 IP 或端口。如果多个入口反复失效，就不能只靠换 IP，需要把入口、中转和落地拆开设计，让入口可以快速替换，后端尽量不直接暴露。

区分封锁、配置与网络问题

误判的代价很高：把配置错误当成封锁会白白浪费 IP，把封锁当成配置问题又会拖长故障时间。可以按“看到 A → 判断 B → 下一步 C”来分流。

国内多地拨测 ping 和 TCP 全部不通，海外从同一 IP 测试正常，说明大概率是 IP 级封锁，下一步更换入口 IP，并检查旧 IP 的暴露途径。ping 正常，但指定端口在国内超时、海外可连，倾向于端口阻断，可以先换端口验证。TCP 握手成功，但 TLS 握手阶段被重置或长时间卡住，要怀疑 SNI 或流量特征被干扰，下一步检查域名、证书和伪装配置。海外也连不上，基本可以排除封锁，应回到服务端排查进程、防火墙和证书。只有某个运营商或时段丢包高、延迟抖动大，多为线路质量问题，可以用 mtr 看丢包出现在哪一跳，再考虑调整中转线路，而不是更换 IP。

DNS、SNI、TLS 与客户端、服务端单节点排查

确定问题集中在某个节点后，按以下步骤逐层检查，每一步都有明确的结果判断： 1. DNS：执行 dig +short node.example.com @223.5.5.5，再对比 @1.1.1.1 的结果。两边结果不一致，或返回明显无关的 IP，说明可能存在 DNS 污染，客户端可以改用 IP 或可信解析。 2. TCP：在国内机器上执行 nc -vz 节点IP 443。返回 succeeded 说明端口可达。持续超时则回到上一节，判断是 IP 封锁还是端口阻断。 3. TLS：执行 openssl s_client -connect 节点IP:443 -servername example.com。出现 Connection reset by peer，或停在 CONNECTED 之后拿不到证书，说明 TLS 或 SNI 层受到干扰。 4. 服务端：用 ss -tlnp | grep 443 确认进程在监听。再用 journalctl -u xray --since "10 min ago" 查看是否有握手失败日志，同时核对证书有没有过期。

5. 客户端：核对 UUID、传输类型、path、SNI 是否与服务端一致。 VMess 还要求设备时间误差不超过 90 秒。 五步都正常但仍然不可用，问题通常不在单个节点，需要转向入口、中转与落地的分层定位。

修复后的覆盖验证：不要只看自己能连上

换 IP、改端口或调整 SNI 之后，单台测试机能连上，不代表问题已经解决。验证至少覆盖三个维度：不同运营商（电信、联通、移动）、不同地区、不同时段。 建议按三步测试： 1. 在国内测试点执行 tcping 入口IP 443，确认端口可达。 2. 执行 openssl s_client -connect 入口IP:443 -servername 你的SNI，检查握手是否完成、证书是否与域名匹配。 3. 通过客户端实际代理执行 curl -x socks5h://127.0.0.1:7890 https://www.gstatic.com/generate_204 -w "%{http_code}"，确认返回 204。 结果可以这样判断： - TCP 通但 TLS 握手超时：多半是 SNI 或流量特征被干扰，下一步换 SNI 或协议做对比。 - 某一运营商全部超时、其余正常：偏向线路或运营商层面的限制，下一步单独调整该运营商的入口。 - 所有测试点正常但用户仍报错：回到客户端订阅与配置检查。 观察期建议持续 24 到 72 小时，并保留服务端连接日志做前后对比。

临时处理的失败边界：哪些情况换 IP 也没用

换 IP、换端口、换 SNI 属于低成本手段，适合偶发的单点封锁，但有明确边界。 第一，新 IP 上线后几天内再次失效，说明问题不在旧 IP 本身，而是入口仍以同样方式暴露。常见情况包括订阅里直接写源站 IP、多个节点共用同一台机器、落地服务器被扫描出特征。 第二，失效集中在晚高峰、白天恢复，更可能是跨境线路拥塞或 QoS，而不是封锁，换 IP 改善有限。 第三，只有部分客户端报错，而服务端日志里看不到这些用户的连接记录，问题通常出在客户端规则、DNS 污染或订阅未更新。 还要注意成本累积。频繁更换 IP 会连带解析变更、订阅刷新、证书重签等工作，用户体验也会反复波动。如果每周都在重复同样的修补动作，说明单节点层面的处理已经到头，应该转向结构调整。

长期思路：入口、转发与后端解耦，以及何时引入专业方案

反复被墙的根因往往是“入口即后端”：用户直连的地址就是落地服务器，一旦被识别，整条链路一起失效。长期做法是分层解耦： - 入口层：准备多个可替换的接入点，可按运营商分组。 - 中转层：负责把流量转发到后端，入口失效时只替换入口，不动落地。 - 落地层：不对用户公开地址，降低源站暴露风险。

配合 XBoard/V2Board 下发多线路订阅，并对每条入口做定时健康检测。入口失效时由运营方调整订阅，而不是让用户自己找可用节点。

这套架构不能让节点不再被封，但能缩小单点失效的影响，缩短切换时间。如果已经出现多个入口或中转频繁失效、换 IP 后短期内反复失效，或难以区分是入口、中转还是落地出了问题，可以参考 Manguo Labs 的机场高可用入口解决方案（https://manguolabs.com/node-firewall/），由其协助做分层定位、多线路规划与切换设计。若只是个别用户的客户端配置有误，先按前文步骤自查即可，不必上升到架构改造。

什么时候这已经不是单点配置问题

如果按上面的步骤排查完，确认问题已经不在单个节点的配置上，而是多个入口或中转反复失效、换 IP 也撑不了多久，那么继续手动修补的意义就不大了。更合适的做法是重新规划入口、中转、落地的分层结构和切换方式。这类需求可以参考 Manguo Labs 的机场高可用入口解决方案。

常见问题

怎么快速判断节点是被墙了，而不是配置出了问题？

分国内、境外两侧看。境外机器 curl 或 openssl s_client 连得上，国内多地 TCP 端口都超时，更像是封锁。两边都失败，先查服务端进程、防火墙和证书。国内能建立 TCP 但 TLS 握手中断，重点看 SNI、证书域名和协议参数是否一致。

只换 IP 能解决被墙吗？

短期内常常能恢复连接，但这只是临时处理。如果新 IP 没多久又失效，说明暴露方式、流量特征或入口结构本身有问题。只换 IP 不改架构，往往只是在重复同一轮循环。

有中转的线路，怎么判断是入口、中转还是落地出了问题？

逐段测：先从国内测入口端口，再从入口机测中转，最后从中转测落地，并对照各段转发日志里的连接记录。哪一段开始超时或被重置，就优先处理哪一段，别一出问题就整条链路一起换。

什么时候该考虑高可用入口方案，而不是继续手动修？

多个入口或中转频繁失效、换 IP 后很快又出问题、需要按入口/中转/落地分别设计切换的时候，单节点修补的成本会越来越高，这时可以评估入口、转发、后端解耦的高可用规划。

总结与下一步

处理节点被墙，可以按这个顺序来：先用国内、境外两侧对比，分清是封锁、配置问题还是线路故障；再按 DNS、SNI、TLS、客户端、服务端逐项排查单个节点；有中转时，按入口、中转、落地分段定位。换 IP、换端口、换协议参数只能临时恢复。入口反复失效的根源通常在于源站暴露和入口跟后端绑死，长期做法是把入口、转发和后端解耦，入口可以替换，切换有预案，源站不直接暴露。
