# 墙配置排查：节点不通，到底是被墙还是配置出错

关键词：墙配置

节点连不上时，先不要急着换 IP。大多数情况属于三类：入口 IP 或端口被封锁、客户端或服务端配置不一致、线路本身丢包或中断。判断方法很直接：境外探测能通、境内 TCP 握手不通，多半是封锁；境内外都不通或握手成功但 TLS/协议报错，优先查配置。本文按 DNS、SNI、TLS、客户端、服务端的顺序给出排查步骤，再按入口、中转、落地分层定位，最后说明反复失效时该怎么调整架构。

## 节点连不上，先判断是“被墙”还是“墙配置”出了问题

很多运营者遇到节点失联，第一反应是“被墙了”，然后直接换 IP。但实际上，相当一部分故障来自配置本身：证书过期、SNI 与证书域名不一致、UUID 或密码改动后未同步到面板、端口未放行、服务进程已退出。这类问题换 IP 不会好转，反而浪费资源。所以“墙配置”排查的第一步，是确认问题属于封锁、配置还是普通网络波动，再决定怎么处理。

直接判断可以先看三点：境外探测能否正常连上该 IP 和端口；服务端日志里是否有来自国内用户的连接记录；同一台服务器上的其他协议或端口是否同时失效。如果境外能连、国内全部超时，且服务端几乎看不到国内来的连接，封锁的可能性较高；如果国内外都连不上，或服务端能看到连接却报握手、认证错误，优先查配置。单个用户报错而其他用户正常，多半是客户端或本地网络问题。

## 区分封锁、配置与网络问题的判断逻辑

三类问题的表现有明显差异。IP 级封锁通常表现为：国内多地对该 IP 的 ping 和 TCP 连接都超时，境外探测正常，服务端进程正常但几乎收不到国内连接。端口或协议特征被干扰时，可能是同 IP 其他端口还能连，或握手阶段出现 connection reset。配置问题则无论国内外都会失败，且服务端日志通常有明确报错。

可以按“看到 A → 判断 B → 下一步 C”处理：看到国内外 TCP 都不通 → 判断服务未监听或防火墙未放行 → 检查进程与安全组。看到 TCP 通但 TLS 握手失败 → 判断证书、SNI 或 ALPN 配置有误 → 用 openssl 验证。看到握手成功但日志提示 invalid user 或认证失败 → 判断面板与节点的用户凭据未同步 → 检查对接配置。看到只在部分时段、部分地区丢包延迟高 → 判断为线路质量问题 → 用多地探测和 mtr 观察跳点，而不是急于更换 IP。

## 单节点排查：DNS、SNI、TLS、客户端与服务端逐层检查

建议按从外到内的顺序逐层排查，每一步确认后再进入下一层：

1）DNS：在国内和境外分别执行 dig 节点域名，确认解析到预期 IP，排除解析被污染或记录未更新。2）端口连通：用 nc -vz IP 端口 或多地 tcping 测试，区分超时与被重置。3）TLS 与 SNI：执行 openssl s_client -connect IP:443 -servername 你的域名，检查证书是否过期、域名是否匹配；若使用 Reality，确认 serverName 与目标站点一致。4）服务端：用 ss -lntp 确认进程在监听，用 journalctl -u xray -f 观察实时日志。5）客户端：核对订阅中的地址、端口、传输方式、路径和 Host 是否与服务端一致，并尝试更新订阅后重连。

如果第 2 步超时而境外正常，基本可转向封锁处理；如果在第 3、4 步发现报错，修正配置后通常即可恢复。只有单节点排查确认无配置问题，才值得继续向入口、中转、落地链路逐段定位。

## 修复后的分层验证：确认墙配置问题真的消失

调整墙配置后，不要只用自己的一台设备连上就判定修复完成。建议按入口、中转、落地三层分别验证。入口层可用 openssl s_client -connect 入口IP:443 -servername 你的SNI，确认握手能返回证书链。如果出现 Connection reset 或长时间无响应，问题仍在入口。中转层在中转机上执行 curl -v --resolve 域名:443:落地IP https://域名，确认到落地的链路正常。落地层则检查服务端日志，确认请求确实到达，没有 TLS 或 UUID 校验报错。

验证时最好覆盖不同运营商和地区，并观察 24 到 72 小时。判断逻辑可以这样走：所有地区立即恢复，多半是配置或证书问题，已经真正修好；只有部分运营商恢复，说明入口仍被定向干扰，下一步应准备备用入口；刚恢复几小时后又出现 context deadline exceeded，说明只是暂时绕开了识别，根因还没有处理。mtr 可以帮助确认丢包发生在哪一跳，结合客户端日志能更快缩小范围。

## 临时处理的失败边界：换 IP、换端口何时不再有效

换 IP、换端口、改 SNI 或更换伪装域名，适合处理单个节点偶发被封的情况，成本低，见效也快。但下面几种现象说明临时处理已经到了边界。第一，新 IP 在几天内又失效，而且失效节奏和上一轮相似。第二，多个入口在同一时间段一起出现握手超时，不像是单点问题。第三，所有节点使用同一套协议参数、同一证书或同一面板域名，配置特征高度一致。第四，订阅内容或面板直接暴露了落地或源站地址，换掉入口后，后端仍然可以被关联。

出现这些信号时，继续调整单个墙配置只是处理表面现象。真正的问题通常在架构层：入口和后端绑得太紧，没有备用线路可切换，也缺少能区分入口、中转、落地故障的监控。这时应停止反复试参数，先整理每次失效的时间、运营商和对应节点，用这些记录找出共同点，再决定是否需要重构链路。

## 入口、转发与后端解耦的长期架构及方案适用范围

长期思路是把入口、转发和后端拆开。入口层准备多条线路，可以随时替换，并通过健康检查自动摘除异常入口。中转层负责把流量转发到落地，自身不直接面向用户公开。落地和源站尽量不出现在订阅或面板中，以降低源站暴露风险。在 XBoard 或 V2Board 中，订阅尽量下发入口域名而不是固定 IP，切换线路时就不必让用户重新导入。同时要统一记录客户端报错和服务端日志，便于下次故障时快速判断是哪一层出了问题。

如果你只是单个节点配置写错，按前文步骤自行排查即可，没有必要引入额外方案。当多个入口或中转频繁失效、换 IP 后短期内又反复出现，或者需要设计入口、中转、落地的切换方案时，可以参考 Manguo Labs 的机场高可用入口解决方案（https://manguolabs.com/node-firewall/）。该方案覆盖多线路与批量部署、XBoard/V2Board 对接，以及客户端检查与故障排查。它的作用是降低单点失效带来的影响，不能承诺节点不被封锁。

## 常见问题

### 怎么快速判断节点是被墙了还是配置写错了？

分别从境内和境外机器执行 nc -vz IP 端口 或 tcping。境外通、境内超时，基本是入口 IP 或端口被封锁；境内外都不通，先查服务端进程、防火墙和监听端口；能握手但客户端报 TLS handshake 失败或 invalid user，就是证书、SNI、UUID 或传输参数不一致。

### 只换端口不换 IP 有用吗？

如果只是单端口被封，换端口可能短期恢复；如果 ping 和所有端口在境内都不通，说明封锁是 IP 级的，换端口无效。换端口后很快又失效，说明流量特征或暴露方式本身被识别，需要从入口架构上处理。

### 有中转的节点不通，先查哪一段？

先查入口到中转：在中转机上看是否收到客户端连接（ss -tnp 或转发程序日志）。收不到，问题在入口段；能收到但连不上落地，在中转机上直接 curl 或 nc 落地端口，判断是中转到落地链路还是落地服务本身故障。

### SNI 和证书配置错误会表现成被墙吗？

会被误判。SNI 与证书域名不匹配、证书过期或 REALITY 的 serverName、publicKey、shortId 不一致时，TCP 能通但握手失败，客户端只显示超时或连接重置。看到 TCP 能通而 TLS 失败，应先核对配置，而不是直接换 IP。

### 换 IP 后几天又失效，说明什么？

说明问题不在单个节点配置，而在暴露面：同一批 IP 段、相同协议特征、订阅或源站地址泄露都可能导致新 IP 很快被识别。这时更适合拆分入口、转发与后端，让入口可替换、源站不直接暴露。

## 总结

墙配置排查的核心是先分类再动手：用境内外双向探测区分封锁与故障，用 TCP 握手和 TLS 报错区分网络问题与配置不一致，再按入口、中转、落地逐段确认故障位置。换端口、换 IP、修正 SNI 与证书属于低成本临时处理，但只适用于单节点或偶发问题。若多个入口反复失效、换 IP 后很快复发，就应把入口、转发和后端解耦，设计可切换的多线路入口，并减少源站暴露。
