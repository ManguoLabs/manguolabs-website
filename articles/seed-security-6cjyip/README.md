# 内鬼常见问题：XBoard 订阅外泄的判断证据与误判边界

关键词：内鬼常见问题、XBoard 订阅共享排查、Token 多 IP、同 IP 多 Token、账号关联追踪

判断内鬼不能只看一个 IP。比较可靠的做法是把同一 Token 的订阅 IP、登录 IP、注册 IP、UA 和节点真实连接 IP 放在同一条时间线上看，再结合同 IP 多 Token 的历史关系做账号关联。最后由人工复核，并排除 NAT、移动网络、旅行、多设备和代理造成的误判。风险评分只能用来安排复核顺序，不能作为封禁的唯一依据。

## 内鬼常见问题的直接回答：先确认是不是"内鬼"

运营者说的"内鬼"，通常指付费用户把订阅链接转卖或分享到群里，或用多个小号配合倒卖。也包括少数先拿到订阅、再把节点地址交给扫描或举报方的人。常见问题主要有三类：订阅被大量陌生设备拉取；节点 IP 很快被封或被测速脚本反复探测；同一批账号反复出现在异常名单里。

直接答案是：只看某个 IP 或某次请求，无法确定谁是内鬼。需要把 Token、注册IP、登录IP、订阅IP、UA 和 Soga 记录的真实连接IP 放在同一条时间线上对照，再结合邀请、支付等历史关系判断。

建议按这个顺序判断：先确认异常确实存在，再看异常是否集中在少数 Token，最后才分析账号之间的关联。风险概率只用于排序和决定复核先后，不是封禁的唯一依据。NAT、校园网、移动网络和旅行都会让正常用户看起来像"多 IP 共享"。

## 异常现象与证据清单：看到什么、意味着什么

第一类证据是订阅请求日志。在 Nginx 访问日志里按订阅路径筛选，例如：grep "/api/v1/client/subscribe" access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head。如果某个 token 参数一天内对应几十个不同 IP，且 UA 同时出现 Clash、Shadowrocket、curl、python-requests 等多种类型，说明链接很可能已经外流。

第二类证据来自节点侧。Soga 等后端上报的真实连接IP，如果长期和订阅IP不重合，说明拉订阅的人和实际连接的人可能不是同一批。

按"看到 A → 判断 B → 下一步 C"的方式处理：
- 同一 Token 多 IP，但 UA 稳定、IP 属于同一运营商网段 → 多半是移动网络切换 → 继续观察，不处理。
- UA 出现 curl 或脚本特征，且请求间隔很规律 → 可能被测速或扫描 → 重置订阅，并保留旧记录。
- 同一 IP 注册多个账号，且邀请关系相互连接 → 疑似团伙 → 转入账号关联排查。

## 自助排查步骤：用现有数据库和日志做一次初筛

不依赖额外系统，也可以先做一轮低成本初筛。步骤如下：

1. 固定时间窗口，例如最近 7 天，导出订阅访问日志。整理时 token 只保留前 6 位，其余掩码，避免排查材料造成二次泄露。
2. 按 Token 统计去重 IP 数和 UA 种类，列出排名靠前的 20 个，并记录每个 IP 首次和最后出现的时间。
3. 在 XBoard 数据库里查询这些用户的基础关系，例如：SELECT id,email,invite_user_id,created_at FROM v2_user WHERE id IN (...)。重点看邀请人是否集中，注册时间是否扎堆。
4. 把订阅IP和 Soga 上报的在线连接IP 逐一对照。只有订阅、没有连接，更像链接外泄或被抓取；订阅和连接都高度分散，更像多人共用同一账号。
5. 按"观察、提醒、重置订阅、限制设备数"的顺序分级处理，每一步都由人工复核后再执行。封号放在最后，并保留证据快照。

这套方法适合账号量不大、偶发异常的场景。如果需要长期追踪历史关系，就要依靠持续的数据积累。

## 处置前的覆盖验证：用多维证据交叉确认

排查内鬼常见问题时，单条线索只能算假设，处置前需要做一次覆盖验证。建议按三步走。第一，把可疑 Token 最近 7 到 30 天的订阅请求 IP、登录 IP 与 Soga 上报的真实连接 IP 拉成同一条时间线，确认三者是否在相同时间窗口内重叠。第二，检查 UA 分布。如果同一 Token 同时出现多种客户端，且分别对应互不相干的地区，而账号主人的登录记录始终集中在一个城市，这是订阅外流的强信号。

第三，重置该账号的订阅链接，观察 24 到 72 小时。看到旧 Token 仍持续被拉取、新 Token 只在主人常用 IP 出现，可以判断原订阅已被转发，下一步再沿关联 IP 查找同一 IP 下的其他账号。如果重置后异常同步消失、也没有旧链接请求，更可能是主人自用设备较多，应降低风险等级，不宜直接处置。

## 失败边界：哪些情况下内鬼判断会出错

即便证据看似完整，以下场景仍容易让判断失效。运营商级 NAT 和校园、企业出口会让大量无关用户共享同一公网 IP，同 IP 多 Token 在这些网络里几乎是常态。移动网络切换基站时 IP 频繁变化，旅行用户一天内跨省甚至跨境也很正常。用户在路由器、软路由或中转机上挂订阅，会让真实连接 IP 与手机登录 IP 长期不一致。

如果面板前有 CDN 或反代，却没有正确透传客户端 IP，日志记录的可能只是 CDN 节点地址，所有 IP 统计都会失去意义。此时应先检查反代是否设置了真实 IP 头，并在 XBoard 侧信任对应来源。日志保留太短、Soga 未开启连接上报，也会让关联链断在中间。因此，风险概率不是封禁唯一依据。分数高只说明值得人工复核，最终处置要结合沟通记录、历史行为和重置后的变化综合决定。

## 常见问题

### 一个 Token 一天内出现多个 IP，就是内鬼吗？

不一定。手机在 Wi-Fi 和蜂窝网络之间切换、运营商 CGNAT、多设备同步订阅、客户端走代理更新订阅，都会产生多个 IP。还要看这些 IP 的地域和 ASN 是否分散、UA 是否明显异常、时间上是否同时活跃、真实连接 IP 是否与订阅 IP 对得上，再决定是否进入人工复核。

### 同一个 IP 下有多个 Token 说明什么？

这种情况可能是家庭或公司共用出口、校园网 NAT，也可能是一个人用多个账号分发订阅。可以查这些账号的注册时间是否集中、注册 IP 是否相同、支付或邀请关系有没有关联，以及历史上是否反复同时出现。只看一次同 IP，证据太弱。

### 订阅 IP 和 Soga 真实连接 IP 不一致正常吗？

通常是正常的。订阅可能通过代理、CDN 或另一台设备拉取，节点连接则来自实际使用的终端。真正值得注意的是同一账号的真实连接 IP 长期同时分布在多个互不相关的地域或网络，并且连接数明显超出正常的多设备范围。

### 账号关联追踪要追多少层？

关联层数越多，噪声越大。常见做法是从可疑账号出发，沿共享 IP、注册 IP、邀请关系向外扩展，并设上限，例如最多 8 层，越外层的结论越需要人工确认。像大型 NAT 出口这类公共节点，应当标记并排除，否则会把无关用户串到一起。

### 风险评分高可以直接封号吗？

不建议这样做。风险评分只是一个概率参考，不能作为封禁的唯一依据。比较稳妥的流程是：分数高的账号先进入人工复核，复核时核对证据链；可以先重置 Token、观察后续行为，必要时联系用户确认，最后再决定是否处理。

## 总结

排查内鬼的关键是证据链，单个 IP 说明不了问题。先收集 Token、注册/登录/订阅 IP、UA 和真实连接 IP，再用长期的历史关系解释同 Token 多 IP、同 IP 多 Token 这两类现象，并通过有上限的关联追踪找出共享网络。风险评分用来安排复核顺序，处理结论要经过人工复核，同时要考虑 NAT、移动网络、旅行、多设备和代理造成的误判。
