防墙误判的直接结论：节点连不上，先别急着换 IP

很多机场运营者收到“节点全挂了”的反馈，第一反应是 IP 被墙，于是立刻换 IP。实际排查中，不少故障来自证书过期、域名解析变更、客户端内核不兼容、服务端进程崩溃，或落地机房线路抖动。防墙误判的关键，是换 IP 之前先用证据区分“被封锁”和“自身出错”。否则新 IP 上线后照样不通，地址资源也白白消耗。

可以先从三点快速判断。第一看影响范围：只有部分运营商或地区不可用，境外探测正常，更接近封锁；境内外全部不通，多半是服务端或配置问题。第二看失败形态：境外连 443 也返回拒绝连接，基本是服务未监听；境内 TCP 能建连但 TLS 握手被重置，才需要进一步怀疑干扰。第三看时间线：故障是否紧跟证书续期、面板更新、内核升级或防火墙规则调整发生。三点都对不上封锁特征时，应先排查配置和服务端。

区分封锁、配置与网络问题：看到什么，判断什么，下一步做什么

建议在境内至少两个运营商的测试点和一个境外测试点同时探测，再按现象对照判断。

境内多运营商 ping 和 TCP 都不通，境外正常：可能是 IP 级封锁。下一步确认同网段其他 IP 是否同样异常，并记录开始时间，再决定是否更换入口。境内 ping 通但指定端口超时，境外正常：更像端口级或协议特征干扰。下一步换一个端口做对照测试，不要直接弃用 IP。境外也报 Connection refused：服务未监听或防火墙拦截，属于服务端问题。下一步检查进程状态与 iptables、ufw 规则。客户端日志出现 x509: certificate has expired 或 tls: handshake failure：证书或 SNI 配置错误。下一步核对证书有效期与域名。只有晚高峰丢包高、延迟大幅抖动：线路拥塞，属于网络质量问题。下一步用 mtr 定位异常跳点，与机房或上游沟通。

把每次判断依据写进故障记录，后续复盘才能分清哪些 IP 是真正被封。

DNS、SNI、TLS、客户端与服务端：单节点排查步骤

确认问题集中在某个节点后，按下面顺序逐层排查，每一步都留下命令输出作为证据： 1. DNS：分别执行 dig +short node.example.com @1.1.1.1 和 dig +short node.example.com @223.5.5.5。两边结果不一致或指向陌生地址，说明可能存在解析污染或记录未更新，应先修正解析。 2. 端口：境内外分别执行 nc -vz 节点IP 443。境外通、境内不通，再进入封锁判断；境外也不通，直接查服务端。 3. TLS 与 SNI：执行 openssl s_client -connect 节点IP:443 -servername node.example.com，查看证书 notAfter 是否过期，SAN 是否包含所用 SNI。 4. 服务端：用 systemctl status xray、journalctl -u xray -n 50 查看崩溃或配置报错，再用 ss -lntp | grep 443 确认端口实际在监听。

5. 客户端：核对 UUID、flow、path、传输协议是否与订阅一致，换另一款客户端交叉测试，排除内核版本不兼容。

五步都正常、只有境内特定线路失败时，才有较充分的理由判定为封锁。

修复后的验证：用多点对照排除防墙误判

调整配置或更换入口后，不要只凭一台客户端恢复连接就下结论。先从国内多个运营商网络对入口执行 TCP 探测，例如用 tcping 或 nc -vz 入口IP 443；再在境外 VPS 上做同样测试。国内超时、境外正常，更可能是入口受到阻断；两边都失败，应回头检查服务端进程、防火墙规则和端口监听，例如 ss -lntp 是否有对应端口。

TCP 能通但客户端仍失败时，用 openssl s_client -connect 入口IP:443 -servername 你的域名 检查握手。看到证书链完整、SNI 对应正确，说明 TLS 层基本正常，下一步应核对客户端 UUID、传输方式和路径。握手阶段被重置，而换 SNI 后恢复，就需要关注 SNI 层面的干扰。验证还要跨越时间窗口，至少观察高峰与非高峰两个时段，并记录每次结果。这样才能区分偶发抖动和持续阻断，减少把配置错误当成被墙的防墙误判。

自助处理的失败边界：哪些情况不该继续换 IP

单节点排查适合处理证书过期、端口未放行、客户端参数不一致这类问题。如果出现以下现象，继续靠换 IP 或改端口通常只能换来短暂恢复：新 IP 上线几天后再次出现国内超时、境外正常；多个入口在相近时间一起失效；入口正常但中转到落地之间频繁丢包；或者只有部分运营商、部分地区的用户持续报障。

这些现象说明问题已经超出单台服务器的配置范围，可能与入口暴露方式、流量特征或链路结构有关。另一个常见边界是缺少观测能力。只有一台测试机、没有分运营商探测、没有按入口、中转、落地分别记录日志时，很难判断故障发生在哪一层。临时方案也有代价：频繁更换入口会导致订阅地址变动，用户侧缓存旧节点，客服压力上升，误判的概率反而更高。到了这个阶段，应该先补齐监控与分层记录，再决定架构层面怎么调整。

长期架构思路与高可用方案的适用边界

长期来看，比较稳妥的做法是把入口、转发和后端解耦。入口层准备多组可替换地址，并持续做分地区健康探测；中转层负责线路选择和故障切换；落地后端尽量不直接对用户暴露，以降低源站暴露风险。订阅侧可以结合 XBoard 或 V2Board 管理多线路节点，入口失效时调整下发内容，不必让每个用户手动排查。批量部署脚本和统一配置模板能减少人为参数差异，从源头上降低防墙误判。

如果你的情况只是单个节点配置写错，按前文步骤自查通常就够了。当多个入口或中转频繁失效，换 IP 后短期内反复出问题，或者需要系统地区分入口、中转与落地故障并设计切换方案时，可以参考 Manguo Labs 的机场高可用入口解决方案（https://manguolabs.com/node-firewall/），其中包括多线路规划、批量部署以及客户端检查与故障排查。需要注意的是，任何架构都只能降低失效频率、缩短恢复时间，不能承诺完全不受阻断。

什么时候这已经不是单点配置问题

如果按上述步骤自查后，确认问题是单节点证书、端口或配置错误，自行修复即可。若排查显示多个入口或中转反复失效，或需要系统性区分各层故障并设计切换策略，可以参考 Manguo Labs 的机场高可用入口方案，评估是否适合你的架构。

常见问题

怎样快速判断节点是被墙还是配置问题？

在境外服务器和境内网络分别对同一入口执行 tcping 或 nc -vz IP 端口，再用 openssl s_client -connect IP:443 -servername 你的域名 检查握手。境外也失败，基本是服务端、证书或配置问题；境外正常、境内多个运营商都超时或被重置，才更倾向于封锁；仅单一运营商异常，多数是线路或局部网络问题。

ping 不通是否就说明 IP 被封？

不一定。很多云厂商或防火墙默认禁 ICMP，ping 不通但 TCP 端口可达的情况很常见。反过来，ping 通但端口不通，也可能只是端口级干扰或服务进程退出。判断应以目标端口的 TCP 连接与 TLS 握手结果为准，并结合服务端日志查看是否收到连接。

换 IP 后几天又失效，说明什么？

如果新 IP 短期内重复失效，往往不是单纯运气问题，可能是入口特征明显、源站直接暴露、域名或证书与旧 IP 关联、流量模式集中等。继续单点换 IP 只是在消耗资源，应考虑入口、转发与后端解耦，并为入口准备可切换的备用线路。

中转正常但用户仍连不上，应该查哪里？

先在中转机上直接 curl 或 nc 落地端口，确认中转到落地是否可达；再看落地服务端日志是否有来自中转 IP 的连接记录，以及落地出口能否正常访问外网。若落地日志无记录，问题在转发规则或中转到落地链路；有记录但无出站流量，问题多在落地出口或路由。

总结与下一步

防墙误判的根源是把所有“连不上”都归结为封锁。正确做法是境内外对照测试，按 DNS、TCP、TLS、协议、客户端逐项排查，再按入口、中转、落地分层定位。临时措施如换端口、换 IP 只能缓解单点问题；若多个入口反复失效、换 IP 后很快复发，应转向入口与后端解耦、多线路切换的长期架构，并保留可复用的排查记录。
