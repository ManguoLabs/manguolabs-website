节点被墙怎么判断：先看现象再下结论

节点"被墙"一般指入口 IP 或端口在国内网络被干扰，常见表现是 TCP 连接超时、握手被重置或丢包严重。但"连不上"不等于"被墙"，配置错误、证书过期、服务端进程退出、本地运营商波动也会有类似症状。判断思路是对比测试：同一节点在海外网络正常、在国内多个运营商同时不通，被墙的可能性才高；如果只有某个客户端或某个用户连不上，优先查配置和本地网络。

结论通常只有三种。第一种是 IP 层封锁，表现为国内 ping 和 TCP 全部超时，海外探测正常。第二种是端口或协议特征被识别，表现为同 IP 的 22 端口能连，代理端口握手失败或被 reset。第三种不是封锁，而是服务端或链路问题，海外探测同样失败。先分清属于哪一种，再决定换端口、换 IP 还是修配置，避免盲目换 IP 后很快又出现同样的问题。

区分封锁、配置错误与本地网络问题

最直接的方法是用"国内一台、海外一台"两个探测点对比，再结合客户端日志。看到国内 tcping 目标端口持续 timeout，海外正常，SSH 端口也不通，判断为 IP 层封锁，下一步是准备新入口而不是改配置。看到国内 SSH 可连，代理端口返回 connection reset by peer 或 TLS 握手中断，判断为端口或协议特征被干扰，下一步是检查伪装方式、SNI 和端口策略。看到海外探测也失败，或客户端日志出现 x509 certificate has expired、invalid user，判断为服务端配置问题，与封锁无关。

本地网络问题也很常见。只有一个用户报障，换手机热点后恢复，多半是该用户的宽带、路由器 DNS 或公司防火墙所致。另一类是时间不同步：VMess 等协议对客户端时间敏感，时间偏差较大时会出现认证失败。区分这三类后，排查范围能明显缩小，也能避免把服务端配置故障误判为被墙，在不必要时浪费 IP 资源。

单节点排查：DNS、SNI、TLS 与客户端的有序步骤

针对单个节点，建议按以下顺序逐层排查，每一步只验证一个变量。（1）DNS：在国内执行 nslookup 你的入口域名，确认解析到的是当前 IP，而非旧地址或被污染的结果，必要时对比 8.8.8.8 与本地 DNS 的返回。（2）TCP：执行 tcping 或 nc -vz IP 端口，超时说明链路或 IP 层有问题，能连通再往下查。（3）TLS 与 SNI：执行 openssl s_client -connect IP:443 -servername 你的域名，检查证书链、有效期和 SNI 是否与配置一致，握手中途断开要重点怀疑干扰。（4）服务端：在服务器上用 ss -tlnp 确认监听端口，用 journalctl 或面板日志查看进程是否报错。（5）客户端：核对协议、UUID、传输方式、路径与 Host 是否和服务端一致，并确认系统时间准确。

若前四步都正常、只有客户端失败，问题基本在订阅或客户端配置；若第二步就失败且海外正常，再按封锁处理。记录每一步的命令输出，后续定位入口、中转与落地哪一层出问题时可以直接复用这些证据。

修复后的分层验证：确认不是“暂时能用”

换 IP、换端口或改配置后，本机能连上只能说明“这一次通了”，还要分层验证。第一步，在入口服务器上执行 ss -tnlp | grep 443，确认监听进程和端口正确。第二步，从国内至少两种网络发起测试，例如电信家宽和移动数据各一组。用 openssl s_client -connect 入口IP:443 -servername 你的SNI 检查握手：能看到证书链并显示 Verify return code: 0，说明 TLS 正常；如果出现 connection reset 或长时间无响应，问题仍在入口。第三步，在中转机和落地机分别查看连接日志，例如 journalctl -u xray --since "10 min ago"，确认流量确实到达，而不是卡在某一跳。

判断逻辑可以这样走：某网络握手失败，同时服务端收不到任何连接，多半是入口线路被干扰；握手成功但落地日志没有请求，应该查中转转发规则；三层日志都正常，用户却仍反馈断流，再回头检查客户端版本和订阅内容。验证建议持续 24 到 72 小时，覆盖晚高峰。只在白天测一次就宣布恢复，是“过几天又被墙”最常见的误判来源。

失败边界：自助处理什么时候不再有效

换 IP、换端口、调整 SNI 这类低成本手段，适合单个入口偶发失效的情况。下面几种信号说明问题已经超出单节点配置。第一种，新 IP 上线几天内又失效，而且时间规律相近，通常说明暴露的是入口的流量特征或地址来源，换地址本身无法根治。第二种，多个入口在同一时段集体异常，往往意味着它们共享了同一段 IP、同一家上游或相同的协议指纹。第三种，ping 能通但 443 握手被重置，或 TCP 能建连、TLS 阶段失败，这比单纯的路由故障更接近针对性干扰。第四种，源站 IP 曾直接写进订阅、面板域名或 DNS 记录，就要假设它已经泄露。

遇到这些情况还反复手动换 IP，只会拉长故障周期，并持续消耗 IP 资源。此时更应该先停下来盘点三件事：入口、中转、落地各自承担什么角色；订阅里到底下发了哪些地址；有哪些服务器的地址直接暴露给了用户。把这三件事理清楚，再决定下一步是调整配置，还是调整架构。

长期架构思路与服务适用边界

想让入口反复被墙的情况变少，核心是把入口、转发和后端解耦。入口层只负责接入，做成可以快速替换的池子，单个入口失效时直接下线并补位，不牵动后端。中转层负责线路选择和流量转发，对用户隐藏落地地址。落地与源站不出现在任何订阅、DNS 记录或面板域名里，以降低源站暴露的风险。在这个基础上，再配合多线路部署、按运营商分组的健康检查，以及 XBoard/V2Board 订阅下发的联动：探测发现入口异常后，及时调整订阅内容，减少用户手动切换节点。需要说明的是，这样的架构只能降低风险、缩短恢复时间，不能承诺某个地址不会被封。

什么时候这已经不是单点配置问题

单个节点偶尔失效，按本文步骤自己排查一般就能处理。如果同类故障跨越多个入口反复出现，或者每次换 IP 后都很快失效，再继续手动处理成本会越来越高，这时可以考虑从架构层面做入口与后端解耦，把多线路和切换机制规划好。

常见问题

怎么快速判断节点是被墙了，还是配置写错了？

在境内和境外各执行一次 `nc -zv IP 端口` 或 `tcping`。境外能通、境内超时，多半是封锁或线路问题；两边都失败，就先在服务端用 `ss -lntp` 确认进程在监听，再看防火墙和安全组。TCP 能通但客户端报 TLS handshake 错误，就重点检查 SNI、证书域名和协议参数是否和服务端一致。

IP 被封后换一个新 IP，为什么过不了几天又不行了？

换 IP 只换掉了地址，源站暴露的路径、协议特征、流量模式和订阅分发方式都没变，新地址很容易再次被识别出来。如果每次换 IP 后都在差不多的时间失效，说明根因在架构层，应该考虑把入口、转发和后端拆开，而不是一直换 IP。

只有部分用户连不上，也能说明节点被墙了吗？

不一定。先按运营商、地区和客户端分组对比。只有某一个运营商失败，可能是这条线路的路由或 QoS 问题；只有某一种客户端失败，更可能是客户端内核版本、配置格式或 DNS 设置不对。所有用户都在同一时间失效，才更符合入口被封锁的特征。

有中转的时候，怎么知道是入口、中转还是落地坏了？

逐跳测试：先从用户侧测入口端口，再在入口机上测中转，最后在中转机上直连落地，同时看各层的转发日志。哪一跳出现连接超时或 reset，问题就在那一层。落地机能直接访问外网而中转到落地不通，通常是这两台机器之间的链路或白名单出了问题。

总结与下一步

节点被墙怎么办，第一步是判断，不是急着换 IP。先用境内外对比把封锁、配置和网络问题分开，再按 DNS、SNI/TLS、客户端、服务端逐项检查，有中转时按入口、中转、落地逐跳定位。换 IP、换端口、调整 SNI 这类临时办法能让服务先恢复，但解决不了反复失效。根因多半在源站暴露和单入口架构上。长期来看，可以把入口、转发和后端解耦，并配上多线路和切换机制，降低单点失效带来的影响。
