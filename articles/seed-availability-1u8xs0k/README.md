# 防墙最佳实践：机场节点失效的分层排查与高可用入口设计

关键词：防墙最佳实践、机场入口高可用、节点被墙排查、入口中转落地分层、换 IP 后反复失效

节点突然连不上时，不一定是被墙。防墙最佳实践的第一步是判断：本地 ping/TCP 是否通、TLS 握手是否完成、客户端日志报的是超时还是证书错误。确认是入口 IP 或端口被封锁后，再决定换 IP、加中转还是调整架构。如果换 IP 后几天内又出现同样问题，说明源站暴露或入口与后端耦合过紧，单点修补的效果会越来越有限，需要转向入口、转发、后端解耦的长期设计。

## 防墙最佳实践的直接答案：先判断，再分层，后解耦

防墙最佳实践不是找一个"不会被封"的协议，而是做好三件事。第一，用证据区分问题类型：封锁、配置错误还是普通网络故障。第二，把入口、中转、落地分层定位，不要整条链路一起推倒重来。第三，让入口可以随时替换，同时不暴露后端，单个 IP 出问题时能快速切走。任何做法都只能降低风险、缩短恢复时间，不存在一劳永逸的方案。
用户反馈通常有三种：全部节点超时；晚高峰某几个节点打不开；换了新 IP 两三天后又不通。可以按下面的规则先做直接判断：
只有部分地区或部分运营商失败，而境外探测服务器正常，优先怀疑入口被干扰。
所有地区同时失败，先查服务端进程、证书和配置。
只有个别用户失败，多半是客户端订阅、系统时间或分流规则的问题。
先按这个顺序缩小范围，再决定要不要换机器、换 IP。这样能少走很多冤枉路。

## 区分封锁、配置与网络问题的判断逻辑

这三类问题表面症状很像，但留下的证据不同，可以按"看到 A → 判断 B → 下一步 C"处理：

看到境内多地 ping 和 TCP 都不通，境外探测全部正常 → 入口 IP 可能已被封锁 → 先别急着改协议，确认是否只有这个 IP 受影响，同机房其他 IP 是否正常。
看到 TCP 端口能连通，但握手后立即断开，境外测试同样失败 → 多半是配置或证书问题 → 检查服务端日志和证书有效期。
看到 TCP 能通、握手偶尔成功，丢包和延迟随时段明显波动 → 可能是线路质量差或特定端口被干扰 → 换端口对比测试，用 mtr -rwc 50 目标IP 查看丢包从哪一跳开始。
看到只有某个客户端失败，其他设备用同一订阅正常 → 客户端问题 → 检查系统时间（偏差过大会导致部分协议认证失败）、订阅是否已更新、内核版本是否过旧。

关键是始终保留对照组：境内探测点、境外探测点、同机的其他端口、同订阅的其他设备。只看单一测试结果，很容易把配置错误当成被墙，结果白白换掉一个本来健康的 IP。

## DNS、SNI、TLS、客户端与服务端的单节点排查步骤

以单个节点为对象，按从外到内的顺序逐层检查：
1. DNS：分别执行 dig +short node.example.com @223.5.5.5 和 dig +short node.example.com @1.1.1.1，对比结果。如果不一致或返回明显异常的地址，说明解析可能被污染或记录尚未生效。此时改用 IP 直连测试，或检查 DNS 记录。
2. TCP：执行 nc -zv 203.0.113.10 443。
 - 返回 Connection timed out，指向网络层阻断或防火墙拦截。
 - 返回 Connection refused，说明服务没有在监听。到服务端执行 ss -tlnp | grep 443 确认。
3. TLS 与 SNI：执行 openssl s_client -connect 203.0.113.10:443 -servername node.example.com，查看证书链和有效期。如果带某个 SNI 时连接被重置，换一个 SNI 却能正常握手，可能存在基于 SNI 的干扰。

4. 服务端日志：执行 journalctl -u xray -n 100 --no-pager。

 - 出现 invalid request user id，说明有流量到达，但客户端 UUID 与服务端不一致。
 - 测试期间完全没有新日志，说明问题出在服务端之前的链路上。
5. 客户端：逐项核对 UUID 或密码、传输方式、path、TLS 设置是否与服务端一致，并确认系统时间准确。
总结一下：服务端没有收到流量，就向入口和线路方向查；收到流量但认证失败，就回头修配置。

## 修复后的分层验证：多视角复测与观察窗口

换 IP、换端口或调整 TLS 后，不要只用本机连通性判断是否恢复。应按层复测：先执行 dig +short entry.example.com @223.5.5.5，再用 @1.1.1.1 对比解析结果，确认入口域名没有被污染或解析到旧 IP。然后执行 openssl s_client -connect 入口IP:443 -servername 你的SNI，确认握手完成、证书链与 SNI 一致。最后用客户端分别连接入口、中转和落地，记录成功与失败的层级。

判断逻辑如下：如果境外探测正常、国内多个运营商都超时，通常是入口受到干扰，下一步应检查该 IP 段和端口；如果入口握手正常，但服务端日志出现 connection reset by peer 或 i/o timeout，问题更可能在中转到落地之间，下一步应单独测试中转出口。验证至少覆盖移动、联通、电信三类网络，并设置 24 到 72 小时的观察窗口，用来区分短时波动和稳定恢复。复测结果建议按时间、运营商和层级记录，之后复盘会更有依据。

## 失败边界：自助处理到哪里就该停下

防墙最佳实践里的自助手段，比如换 IP、换端口、更新内核和客户端、修正 SNI 与证书，主要解决单节点的配置问题，或偶发性的干扰。下面几种信号说明问题已经超出单点修复的范围：新 IP 上线几天后又失效；同一 IP 上多种协议、多个端口同时不可用，这类情况多半是 IP 级封锁，换端口意义不大；只有特定 SNI 握手失败，说明可能是域名或特征层面的识别；同一机房或 ASN 的多台机器先后出问题，说明暴露面在扩大，并非偶然。

这时继续换 IP，本质上只是在消耗资源。常见的根因包括：订阅内容外泄，导致入口地址被批量收集；落地或源站 IP 直接写在配置里，自身暴露在外；所有入口集中在同一网段，形成单一故障域。到了这个阶段，应该停止逐台修补，转向梳理链路结构。任何措施都只能降低风险、缩短恢复时间，不存在一劳永逸的方案。

## 常见问题

### 怎么判断节点是被墙了，而不是配置写错了？

在国内机器上用 tcping 或 nc -vz 测试入口端口，同时在海外机器上测同一端口。海外通、国内超时或被重置，多半是封锁；两边都不通，先查服务进程、防火墙和端口监听（ss -lntp）。如果 TCP 通但客户端报 TLS handshake 或证书错误，优先检查 SNI、证书域名和时间同步。

### 换 IP 能解决被墙问题吗？

换 IP 是临时处理手段，能快速恢复，但如果源站 IP 通过订阅、域名解析历史或面板地址暴露，新 IP 可能很快再次失效。换 IP 后短期内反复出现，就应排查暴露途径并考虑入口与后端分离。

### 入口、中转、落地分别出问题时表现有什么不同？

入口故障通常表现为国内多地同时连接超时或握手失败；中转故障表现为入口可连但无法转发到后端，日志出现 upstream 连接超时；落地故障则是链路建立但访问目标网站失败或出口 IP 异常。逐段用 curl 或 tcping 测试即可分层定位。

### 小规模机场有必要做多入口和中转吗？

用户少、节点少时，先做好证书、SNI、DNS 配置检查和备用入口即可。只有当多个入口或中转频繁失效、手动切换成本明显上升时，才值得投入多线路与批量部署。

### XBoard/V2Board 面板与防墙有什么关系？

面板域名和节点地址如果直接暴露源站，会增加被关联封锁的风险。建议面板与节点使用不同域名和服务器，节点下发地址指向入口层而非后端真实 IP，并定期核对订阅中实际下发的地址。

## 总结

防墙最佳实践的核心是先判断再处理：用国内外对比测试区分封锁、配置与网络问题，按 DNS、SNI、TLS、客户端、服务端逐项排查单节点，再按入口、中转、落地分层定位。换 IP、换端口属于临时手段，有边界。若问题反复出现，根因多在源站暴露与架构耦合，长期应采用入口、转发、后端解耦并配合多线路切换。没有任何方案能保证不被封锁，目标是降低暴露风险并缩短恢复时间。
