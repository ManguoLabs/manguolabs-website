# 内鬼如何排查：XBoard 订阅泄露的证据链与人工复核方法

关键词：内鬼如何排查、XBoard 订阅泄露排查、Token 多 IP 分析、账号关联追踪、订阅共享审计

排查内鬼不能靠单个 IP 下结论。要先把 Token、注册 IP、登录 IP、订阅请求 IP、UA 和节点侧真实连接 IP 串成证据链，再看同 Token 多 IP、同 IP 多 Token 和账号之间的历史关系。最后根据风险评分进行人工复核，排除 NAT、移动网络、旅行和多设备造成的误判。风险概率只能作为线索，不能当作封禁的唯一依据。

## 内鬼如何排查：先建证据链，再下结论

排查内鬼，要回答的问题是：谁把订阅链接、节点地址或配置带到了不该出现的地方。对 XBoard 运营者来说，常见表现有三种：新节点上线不久就被扫描或阻断；订阅链接出现在公开群组；某个套餐的流量突然放大。结论先说：不要凭单一 IP 或一次异常定性。应把 Token、注册 IP、登录 IP、订阅拉取 IP、UA，以及 Soga 等节点后端记录的真实连接 IP 按时间线串起来，找出同一个人在多个环节留下的重叠痕迹。

成本较低、能马上做的办法有三类。第一，从 Nginx 访问日志和面板数据里提取订阅请求，找出被异常多 IP 和客户端拉取的 Token。第二，用专属分组或“金丝雀”节点缩小泄露范围。第三，对可疑账号重置 Token，观察旧 Token 是否仍被请求。这些结果都只是风险概率，风险概率不是封禁唯一依据。处置前应保留人工复核和申诉渠道。

## 异常现象与证据清单

先验证“确实存在内鬼”这个假设。值得关注的信号包括：只分配给少数用户组的节点很快失效，其他节点却正常；某个 Token 一天内被大量不同 IP 拉取订阅，UA 里既有 Clash、Shadowrocket、sing-box，也夹杂 curl、python-requests 这类脚本特征；同一 IP 段短时间内批量注册新账号；节点侧在线 IP 数长期高于该用户的设备上限。

证据建议按字段整理：Token 与用户 ID 的对应关系、注册时间与注册 IP、登录 IP 与时间、订阅拉取的 IP/时间/UA、节点后端上报的真实连接 IP，以及节点被阻断或被扫描的时间点。存档时要脱敏，Token 只保留前几位或哈希值，避免日志本身变成新的泄露源。判断逻辑举例：看到节点失效前不久，某 Token 首次被陌生 IP 段拉取 → 判断该 Token 可能已外流 → 把它列入重点观察，先不急于封号。

## 低成本自助排查步骤

1. 统计每个 Token 的订阅来源 IP 数（默认路径为 /api/v1/client/subscribe，如自定义了订阅路径请替换）：
awk '/client\/subscribe/{match($7,/token=[^& ]+/);print substr($7,RSTART+6,6),$1}' access.log | sort -u | awk '{print $1}' | uniq -c | sort -rn | head
2. 查看订阅请求的 UA 分布，留意脚本类 UA：
awk -F'"' '/client\/subscribe/{print $6}' access.log | sort | uniq -c | sort -rn
3. 把排名靠前的 Token 与节点后端的真实连接 IP 对照。如果只拉取订阅、从不连接，更像是转卖或抓取节点信息。
4. 新建金丝雀节点，只分配给可疑用户组。该节点被扫描或阻断，说明泄露范围可能就在这组用户里，下一步可以继续拆分分组。

5. 重置可疑 Token 后观察日志：旧 Token 仍被多个 IP 请求，基本可以确认链接已外流。若被确认为泄露源，再转人工复核。

## 验证排查结论：用重置对照确认内鬼线索

锁定可疑账号后，不要直接封禁，先做一次可回溯的对照验证。步骤如下：1. 导出该账号近 7 天的订阅请求 IP、UA 与 Soga 真实连接 IP，作为基线；2. 在后台重置该用户订阅 Token，并通知本人更新；3. 观察 24-72 小时内新 Token 的订阅来源；4. 与基线逐项比对。

判断逻辑是：如果新 Token 很快又出现在基线中那批陌生 IP 段，并且 UA 同时出现 Clash、Shadowrocket、v2rayN 等多种客户端，说明链接仍在被持续转发，内鬼嫌疑明显上升。如果新 Token 只出现在用户常用的一两个网段，则更可能是旧链接外泄，而不是主动分发。检查 Nginx 日志时，可以用 grep "client/subscribe" access.log 筛出订阅请求，并把 token 参数打码后再存档或共享，避免二次泄露。

## 失败边界：哪些情况不能直接认定内鬼

最常见的误判来自网络环境本身。运营商 CGNAT 和校园网会让大量无关用户共用同一出口 IP，造成同 IP 多 Token 的假象。移动网络切换基站、出差旅行、手机和电脑同时使用，会让同一 Token 在一天内出现多个城市的 IP。用户自己挂代理去更新订阅时，订阅 IP 记录的是代理出口，不是真实位置。

还有一种是配置问题：面板前面有 CDN 或反代，但没有正确设置 set_real_ip_from 和 real_ip_header，结果所有请求都记成 CDN 节点 IP。看到大量账号共用少数几个 IP，先检查反代配置，再分析用户行为。

因此，风险概率不是封禁唯一依据。高分账号应当进入人工复核，结合历史关系和连接证据判断；证据不足时，优先采取重置 Token、限制设备数或联系用户核实等可撤销的处置。

## 长期架构与服务适用边界

小规模面板靠手工 SQL 和日志通常就能处理零星个案。但内鬼排查真正依赖长期历史关系，比如某个 IP 三个月前和哪些账号共用过，或者被封账号的关联网络是否换了新号继续分发。这类查询如果直接跑在 XBoard 主库上，会拖慢业务。比较稳妥的做法是把审计数据写入独立 MySQL，将 Token、注册 IP、登录 IP、订阅 IP、UA 和 Soga 真实连接 IP 统一建模，再通过仪表盘查看关联链路和风险分布。

## 常见问题

### 同一个 Token 出现多个 IP，就能认定是内鬼吗？

不能。移动网络切换基站、家庭宽带重新拨号、公司 NAT、旅行和多设备都会产生多个 IP。更合理的做法是看 IP 的地理和 ASN 分布、出现时间是否重叠、UA 是否差异很大，以及节点侧真实连接 IP 是否同时活跃。证据要互相印证后再交给人工复核。

### 同一个 IP 下有多个 Token，说明什么？

这可能是共享网络，比如校园网、公司出口或运营商 CGNAT，也可能是一个人操作多个账号或在转售订阅。判断时要看这些账号的注册时间是否接近、注册 IP 是否相同、邀请关系和支付行为是否有关联，不能只凭同 IP 做批量处理。

### 为什么要看 Soga 等节点侧的真实连接 IP？

订阅请求 IP 只能说明谁拉取了配置，不代表谁在用节点。订阅可能经过转换服务或代理拉取。节点侧的真实连接 IP 更接近实际使用者，把它和订阅 IP 对照，才能区分“只拉取一次”和“多人长期同时使用”。

### 账号关联追踪到第几层就该停止？

传播追踪可以按注册 IP、登录 IP、邀请关系等逐层展开，常见做法是设置层数上限，比如最多 8 层，防止关联无限扩散。层数越深，证据通常越弱。深层关联只适合用来列出待查对象，不适合直接处置。

### 风险评分高就可以直接封禁吗？

不建议这样做。风险概率不能作为封禁的唯一依据。高分账号应该先由人工复核原始证据，再按情况重置 Token、发通知、限速或要求说明，并留存复核记录，便于用户申诉和后续对照。

## 总结

排查内鬼的核心是建立证据链，而不是抓单个 IP。具体做法是：收集 Token、注册/登录/订阅 IP、UA 和真实连接 IP，保留历史关系；分析同 Token 多 IP 和同 IP 多 Token；通过账号关联最多追踪 8 层；再用风险评分排出复核顺序。NAT、共享网络、移动网络、旅行、多设备和代理都会造成误判，风险概率不是封禁的唯一依据，最终处置要经过人工复核。
