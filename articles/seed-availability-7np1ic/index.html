节点被墙怎么办：先确认是不是真的被墙

节点“被墙”后，第一件事不是马上换 IP，而是先确认问题出在哪一层。很多所谓的被墙，其实是证书过期、域名解析变更、服务端进程退出，或者客户端配置没有同步。判断标准很直接：在国内网络下，ping 和 TCP 端口都不通；在海外机器上，同一 IP 和端口完全正常；服务端日志里也没有任何来自国内的连接记录。满足这几条，才比较接近 IP 被封锁。如果只是某个端口不通、其他端口可达，更可能是端口级或协议特征级的阻断。

确认被墙后，短期办法有几种：更换入口 IP 或端口、套一层中转，或者切换到流量特征不太明显的传输方式。这些办法只能恢复可用，不能消除再次失效的风险。如果同一批节点换 IP 后几天内又不可用，说明问题已经不在单个节点，而在入口的暴露方式和整体架构。这时需要按入口、中转、落地分层定位，再考虑解耦设计。下面先从最容易误判的地方开始排查。

区分封锁、配置与网络问题

用对比测试可以把三类问题分开。准备一台国内测试机和一台海外测试机，对同一个 IP 和端口分别执行 ping 与 nc -zv IP 443（或 tcping），再按结果判断：

看到国内、海外都不通 → 多半是服务端或机房问题，比如进程未启动、防火墙未放行、机器宕机 → 去服务端执行 ss -tlnp 确认端口在监听，并检查云厂商安全组。 看到海外通，国内 ICMP 和所有 TCP 端口都不通 → 较接近 IP 级封锁 → 换一个国内运营商复测，排除单一线路故障。 看到国内 TCP 能建立，但很快被 reset，或日志出现 TLS handshake timeout → 可能是协议特征或 SNI 层面的干扰，也可能是证书配置错误 → 进入下一节做 TLS 检查。 看到只有部分地区或部分用户报错 → 通常是本地运营商路由或客户端问题，而不是节点被墙。

还要看时间维度。只在晚高峰变慢、白天正常，多半是线路拥塞；某个时间点之后彻底断开且持续不恢复，才更像封锁。

DNS、SNI、TLS、客户端与服务端单节点排查步骤

对单个节点，建议按下面顺序逐层排除：

1）DNS：在国内执行 dig 节点域名 +short，与海外结果对比。如果解析结果不一致或指向异常地址，说明解析被污染或记录未生效。可以改用可信 DNS，或直接用 IP 测试。 2）TCP：执行 nc -zv IP 443，确认端口可达，再继续往上查。 3）TLS 与 SNI：执行 openssl s_client -connect IP:443 -servername 你的域名，检查证书链是否完整、是否过期、域名是否匹配。如果换成其他 SNI 能握手而原域名不行，需要怀疑该域名被针对。 4）服务端：执行 systemctl status xray（或你实际使用的内核服务），再用 journalctl -u xray -n 100 查看日志。如果出现大量 TLS handshake error 或 failed to read request，优先排查配置和证书，不要急于认定被墙。 5）客户端：核对订阅是否为最新，UUID、端口、传输方式、path、SNI 和跳过证书验证等设置是否与服务端一致。同时检查系统时间偏差，部分协议对时间比较敏感。

走完这五步，如果仍然是“IP 不可达且只针对国内”，再进入入口、中转、落地的分层定位和更换入口流程。

处理后如何验证：从入口到落地逐层确认恢复

换 IP、换端口或调整配置之后，“客户端能连上了”不等于问题已经解决，要按层验证。先在国内多个运营商网络（电信、联通、移动各一条）测入口 TCP 连通，可用 tcping 203.0.113.10 443。端口通但握手失败时，再用 curl -v --resolve node.example.com:443:203.0.113.10 https://node.example.com/ 看 TLS 阶段。日志停在 Client hello 之后没有回包，多半是 SNI 或握手特征被干扰；证书报错则先查域名与证书是否匹配。

入口正常后，在中转机上用 curl 直连落地端口，确认转发规则和落地服务存活。最后对照服务端 access log：同一时段日志里没有新连接，说明流量没到服务端；有连接但很快断开，就回头查协议参数和时间同步。恢复后建议持续观察 24 到 72 小时，并记录每个运营商的成功率变化。只有一个运营商恢复、其他仍异常时，应判定为部分可用，先别把这次处理当作已解决。

临时处理的失败边界：什么情况下换 IP 不再有效

换 IP 是成本最低的应急手段，但它只解决“这个地址被识别”的问题，解决不了“为什么会被识别”。出现以下现象时，可以判断临时处理已经到了边界：

- 新 IP 上线后数小时到几天内再次失效，节奏和上一次相近。 - 同一机房、同一网段的多个入口同时出问题。 - 换了 IP 但沿用原域名后很快失效，说明域名或 SNI 本身可能已被标记。 - 订阅内容或面板接口直接暴露了后端真实地址，被识别的是源站而不是某个入口。

看到反复失效且间隔越来越短时，说明暴露路径没有切断，继续换 IP 只会持续消耗地址和用户信任，下一步应转向排查暴露来源，比如订阅泄露、源站直连、配置特征过于集中等。另外，单入口架构下任何一次处理都意味着全体用户中断。只要恢复依赖人工发现、人工换 IP、人工改订阅，就很难把影响控制在可接受范围内。到这一步，问题已经不属于单节点配置，而是架构问题。

长期架构与服务适用边界

长期思路是把入口、转发和后端解耦。入口层用多条线路、多个地址分散风险，只负责接入；中转层承担调度和切换；落地与源站不对外暴露真实地址，面板和订阅接口也和节点流量分开。配套做法包括：对每个入口做定时健康检查，失效时由订阅层下发备用入口，而不是全量重建；在 XBoard/V2Board 中按线路分组管理节点，并支持批量部署，换线时不用逐台手改。这样做不能让节点不再被干扰，但能缩小单点失效的影响，缩短恢复时间。

常见问题

怎么快速判断节点是被墙了，还是服务端挂了？

分别从国内和海外测试同一个 IP 和端口，可以用 nc -vz IP 端口，或 curl -v https://域名。海外通、国内不通，偏向封锁；两边都不通，先查服务进程、防火墙和证书；国内能 ping 通但 TCP 端口超时，可能只封了端口，可以先换端口验证。

换了 IP 后很快又不能用了，原因是什么？

常见原因有：新 IP 仍挂在原来已暴露的域名或订阅上；协议特征和 TLS 指纹没有变；同一个源站 IP 直接作为入口对外暴露。只换 IP 不改暴露面，同样的情况很可能再次出现。应该检查订阅里下发的地址、DNS 解析记录，以及后端有没有直接暴露。

只有部分用户连不上，算被墙吗？

不一定。如果集中在某个运营商或地区，可能是线路质量问题、运营商 QoS，或该地区的局部封锁。按运营商分别做 mtr 和 TCP 测试；如果只有单一客户端异常，再查客户端版本、时间同步、SNI 和 ALPN 设置。

入口、中转、落地分别出问题时，表现有什么不同？

入口出问题时，国内连入口的 TCP 或 TLS 直接失败；中转出问题时，入口能连上，但从入口到落地的转发超时；落地出问题时，链路能建立但拿不到外网数据，或者 DNS 解析失败。逐跳在每一层上用 nc 或 curl 测下一跳，就能判断问题在哪一层。

总结与下一步

处理节点被墙，先用国内和海外的对照测试区分封锁、配置错误和网络问题，再检查 DNS、SNI/TLS、客户端和服务端，然后按入口、中转、落地逐层定位。换 IP、换端口只能临时恢复；如果问题反复出现，根因通常在于源站暴露和单点结构。长期做法是把入口、转发和后端解耦，准备多条线路，并设计切换流程。
