# 节点疑似被墙如何排查：从 DNS、TLS 到入口/中转/落地分层定位

关键词：墙如何排查、节点被墙判断、入口中转落地分层排查、机场节点高可用

节点突然连不上，先别急着换 IP。正确的“墙如何排查”顺序是：境外网络能连通而国内不通，且 ping/TCP 握手在国内多地都失败，才更接近被封锁；国内外都不通，多半是服务端或配置问题。本文按 DNS、SNI、TLS、客户端、服务端逐层检查，再拆分入口、中转、落地定位故障，最后说明反复失效时该怎么调整架构。

## 墙如何排查：先看现象，再做境内外对照

排查节点是否被墙，关键是对照测试：同一台服务器，分别从国内和境外访问，比较结果。如果从境外看，TCP 端口、TLS 握手和代理协议都正常，而国内多个地区、多个运营商同时超时，基本可以判断入口 IP 或端口被封锁。如果境外也连不上，问题多半出在服务端配置或进程本身，与墙无关。

用户侧常见三类现象。第一类：客户端测延迟显示超时或 -1，但订阅能正常更新。第二类：能连上，但几分钟后断流，网页时开时不开。第三类：只有某个运营商或某个省份的用户反馈不可用。第一类最接近整个 IP 被封；第二类常见于流量特征被识别后受到干扰或限速；第三类多是局部线路质量或运营商策略问题。运营者收到投诉时不要急着换 IP。先记录四项信息：故障开始时间、受影响的地区与运营商、客户端类型、所用协议。这些信息决定后面该查哪一层，也能避免换了 IP 却没找到真正原因。

## 区分封锁、配置与网络问题

可以按下面三种情况判断：
1. 国内 ping 不通，TCP 所有端口都不通，境外全部正常：判断为 IP 级封锁。下一步确认同网段其他 IP 是否也受影响。
2. ping 正常，只有代理端口在国内超时，其他端口可达：倾向于端口封锁或针对特定协议的阻断。下一步换一个端口做对照。
3. TCP 能连通，但 TLS 握手阶段被重置或长时间无响应：可能是 SNI 或 TLS 指纹受到干扰。下一步更换 SNI，或检查证书与 ALPN 配置。

配置问题的特征是境内外一起失败。服务端日志会出现 invalid user、failed to read request header 之类的报错，或者证书过期导致握手失败，这时换 IP 没有意义。网络问题通常表现为晚高峰丢包率升高，mtr 在某一跳之后持续丢包但没有彻底中断，到凌晨又恢复。建议用 itdog、boce 等多地拨测工具，从多个省份、三大运营商同时测试 TCP 端口，再用一台境外 VPS 做对照，先把可能性缩小到墙、配置、线路中的一种。

## DNS / SNI / TLS / 客户端 / 服务端单节点逐项排查

单节点排查建议从外到内进行，每一步确认正常后再进入下一步：
1. DNS：在国内机器执行 nslookup node.example.com 223.5.5.5，与境外解析结果对比。如果返回异常 IP 或没有结果，说明域名可能被污染，可以先让客户端直连 IP 验证。
2. TCP：执行 tcping 服务器IP 443 或 nc -zv 服务器IP 443。国内超时而境外成功，就是 IP 或端口层的阻断。
3. TLS/SNI：执行 openssl s_client -connect 服务器IP:443 -servername 你的域名，看握手能否完成，证书链和有效期是否正确。如果换一个 SNI 后恢复，问题集中在 SNI。
4. 服务端：用 ss -tlnp 确认端口在监听，再用 journalctl -u xray -f 看实时日志。客户端连接时日志毫无输出，说明流量根本没有到达服务器。
5. 客户端：核对 UUID、端口、传输方式和 TLS 设置是否与服务端一致。使用 VMess 时，还要确认客户端与服务器的系统时间相差不超过 90 秒。

如果单节点检查全部通过，用户仍反馈不可用，问题通常已经超出单个节点，需要转向入口、中转、落地的分层定位。

## 修复后的覆盖验证：多运营商、多时段与两端日志

换了 IP、端口或域名后，不能只看自己这一条宽带能不能连上，验证要分三层。第一层是国内多运营商探测：分别在电信、联通、移动环境执行 tcping 1.2.3.4 443 检查 TCP 是否可达，再用 curl -vk --resolve example.com:443:1.2.3.4 https://example.com 检查握手。如果 TCP 能连通，但日志停在 Client hello 之后，随后出现 Connection reset by peer 或超时，问题通常发生在 SNI 或 TLS 层，而不在路由层。

第二层是境外对照：同样的命令在海外机器上执行正常，说明服务端本身没有问题；如果海外也失败，就该回头检查证书、监听端口和防火墙规则。第三层是两端日志对照：客户端报错的同一时间点，服务端 Xray 或 sing-box 的 access log 里如果完全没有这个来源的连接记录，说明流量在入口之前就被拦截了。另外，封锁常常有滞后，修复后建议连续观察 24 到 72 小时，晚高峰也要单独测一次，再判断是否真正恢复。

## 临时处理的失败边界：换 IP 为什么只能止血

换 IP、换端口属于低成本止血手段，但适用范围很明确。可以按下面的逻辑判断：

1. 只有某个端口不通，换个端口就恢复，说明是端口级干扰，换端口能暂时缓解。
2. 所有 TCP 端口都不通，但 ping 仍有回应，大概率是 IP 级封锁，换 IP 能暂时恢复。
3. 新 IP 几天内又失效，说明 IP 只是表象，应该排查域名、证书、流量特征有没有一起被带到新机器上，以及订阅内容是否已经外泄。

如果每次只换 IP，域名、SNI、协议参数和订阅地址都保持不变，入口很容易被再次识别。另一个常见误区是没有记录：哪个 IP 在什么时间、哪个运营商下失效，都没有留存，就无法区分是单点被封还是整体策略问题。建议至少维护一张表，记录入口地址、上线时间、失效时间、失效现象和受影响的运营商，作为后续判断根因的依据。

## 长期架构与服务适用边界：入口、转发与后端解耦

入口反复失效时，更稳的思路是把入口、中转和落地拆开。用户只接触可替换的入口层；中转负责线路优化；落地不直接暴露给用户，以降低源站暴露风险。入口准备多条线路的地址池，配合健康检查和域名层切换。在 XBoard 或 V2Board 中，可以按入口分组下发节点，某个入口失效时只替换这一层，订阅结构和落地配置不用变。批量部署时还应避免所有入口共用同一证书、同一套参数，防止一个被识别就整批牵连。

如果只是单节点配置错误、证书过期或端口没放行，按前文自查通常就能解决，不需要引入复杂方案。当多个入口或中转频繁失效、换 IP 后短期内又反复出现，或者需要明确区分入口、中转与落地故障并设计切换流程时，可以参考 Manguo Labs 的机场高可用入口解决方案（https://manguolabs.com/node-firewall/），它覆盖链路规划、客户端检查和故障排查。任何架构都只能降低失效频率和恢复时间，无法让节点永远不被封锁。

## 常见问题

### 怎么快速判断是被墙还是服务端挂了？

在境外 VPS 上执行 curl -v 或 nc -zv 目标IP 端口，如果境外通、国内多地不通，偏向封锁；如果境外也不通，先查服务端进程（systemctl status）、防火墙规则和端口监听（ss -lntp）。

### ping 不通就一定是 IP 被封了吗？

不一定。很多云厂商默认禁 ICMP，安全组也可能拦截。应同时测 TCP 端口：ping 不通但 TCP 握手正常，说明 IP 没被整体封；ping 和 TCP 在国内都失败而境外正常，才更可能是 IP 级封锁。

### 只有部分用户连不上该怎么排查？

先按运营商和地区分组。只集中在某一运营商，可能是该线路丢包或局部干扰；集中在特定客户端版本，检查协议参数和 SNI、TLS 指纹配置；分布零散则查用户本地 DNS 和系统时间。

### 换了新 IP 很快又不通，问题出在哪？

常见原因是暴露面没变：同一域名、同一证书、同一协议特征或订阅泄露，新 IP 很快被关联。这时单纯换 IP 只能临时缓解，需要从入口、转发、后端解耦的角度调整架构。

## 总结

墙如何排查的核心是先排除配置和网络问题：用境内外对照测试区分封锁与故障，再按 DNS、SNI、TLS、客户端、服务端逐项检查，并按入口、中转、落地分层定位。换 IP、换端口只是临时手段，如果多个入口反复失效，就需要把入口、转发和后端解耦，并配好切换机制，以降低单点暴露的影响。
