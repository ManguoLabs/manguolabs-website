# 墙常见问题：节点连不上是被封还是配置错？分层排查与长期思路

关键词：墙常见问题、节点被墙怎么判断、入口中转落地排查、SNI TLS 握手失败、换IP后又失效

节点突然连不上，不一定是被墙。先在境外机器上测同一节点：境外能通、境内不通，多半是入口被封或被干扰；两边都不通，先查配置、证书和服务端进程。之后按 DNS → SNI/TLS → 客户端 → 服务端单节点逐项排查，再按入口、中转、落地分层定位，才能确定是临时换 IP 能解决，还是需要调整架构。

## 节点“被墙”的常见表现与直接判断

关于墙的常见问题，最直接的答案是：用户说“节点被墙了”，多数时候只看到了结果，不一定是原因。真正的封锁通常有比较稳定的特征。从国内访问某个入口 IP 时，所有端口都超时，或者 ping 不通但境外探测正常，而且同一网段的多个用户、多家运营商同时出现。如果只有个别用户连不上、只有某个客户端报错，或者只在更新配置之后才失效，优先考虑配置或网络问题。

建议先收集三类信息：失效的是哪个入口或域名，从什么时间开始，影响的是哪些运营商和地区。然后对照日志判断。看到 i/o timeout，且多地同时超时，说明入口 IP 或端口可能被阻断，下一步做境内外对照探测。看到 connection reset by peer，说明链路上可能存在干扰，也可能是服务端主动断开，下一步查看服务端日志。看到 tls: handshake failure，多半是证书或 SNI 配置不一致，下一步检查域名与证书。先分清现象，再决定是否换 IP，可以少走很多弯路。

## 区分封锁、配置错误与普通网络故障

三类问题的判断依据不同。第一类是封锁，典型特征是“境内不通、境外正常”。同一个 IP:端口，用境外 VPS 执行 nc -zv IP 443 能成功，境内多地执行同样的命令全部超时。有时 IP 整体不可达，有时只是某个端口或某种协议特征被干扰。第二类是配置错误，表现为境内外都失败，或者服务端根本没有监听端口。常见原因包括 UUID 或密码不匹配、传输方式写错、证书过期，以及面板下发的参数与后端实际配置不一致。第三类是普通网络故障，表现为高丢包、晚高峰明显变慢、某个运营商单独异常，换线路或换时段后能恢复。

判断时可以用一个简单矩阵。境外通、境内不通，倾向封锁或线路问题。境外也不通，先查服务端。境内部分运营商不通，倾向路由或运营商侧问题。只有握手失败而 TCP 能连通，倾向 TLS、SNI 或协议特征问题。把结论写进工单，再决定是修配置、换线路还是换入口，避免一律按“被墙”处理，结果把配置错误掩盖过去。

## 单节点排查步骤：DNS、SNI、TLS、客户端与服务端

针对单个节点，建议按下面的顺序逐层排查：
1. DNS：执行 nslookup 你的域名，并与 dig @8.8.8.8 的结果对比。如果解析到异常 IP 或无结果，可能是解析污染或记录配置错误，可以改用 DoH 或检查解析记录。
2. 端口：在服务端执行 ss -tlnp | grep 443，确认端口正在监听；在境外执行 nc -zv IP 443，确认端口可达。
3. TLS 与 SNI：执行 openssl s_client -connect IP:443 -servername 你的域名，检查证书域名和有效期是否匹配。Reality 节点要确认 serverName 与目标站一致。
4. 客户端：确认内核版本支持所用协议，订阅已经更新，并查看本地日志中的具体报错。
5. 服务端：执行 journalctl -u xray -n 100，或查看后端日志，确认请求是否到达。

如果请求根本没有到达服务端，问题在入口之前；如果请求到达后被拒绝，问题在认证或协议配置。逐层排除后仍是“境外通、境内不通”，才把它当作入口被封处理，进入换 IP 或切换线路的流程。

## 修复后的覆盖验证：多运营商、多地区、多时段

换 IP、改 SNI 或调整配置后，只在一台电脑上连通，说明不了问题已经解决。建议按以下顺序做覆盖验证：
1. 从电信、联通、移动三类网络分别测试入口。先用 tcping 入口IP 443 确认 TCP 能否建立，再执行 curl -v --resolve 你的SNI域名:443:入口IP https://你的SNI域名，确认 TLS 握手能完成，证书链也正确。
2. 在中转机上执行 ss -tnp | grep :443，确认有来自入口的连接，并且连接没有大量堆积在 SYN-RECV 状态。
3. 在落地机上执行 journalctl -u xray --since "10 min ago"，查看是否出现正常的 accepted 记录。

判断逻辑如下：如果 TCP 能通，但 curl 卡在 Client Hello 后超时，问题多半出在 SNI 或 TLS 层，下一步应检查域名特征和证书。如果只有某一家运营商失败，先按线路问题处理，不要急着整体换 IP。

验证还要覆盖晚高峰，并持续观察 24 到 72 小时。短时间内能连通，不能当作已经恢复稳定的结论。

## 自助处理的失败边界：什么时候该停下来

换 IP、换端口、调整 SNI 这类低成本手段，适合处理单个节点偶发不可用的情况。出现下面几种信号时，继续自助处理的收益会明显下降。

第一，新 IP 只能撑几天，失效周期还越来越短。这通常说明暴露的是某种共性特征，单个地址只是表象。第二，多个入口在同一时段一起失效，而落地机日志一切正常。这时问题集中在入口层，逐台排查很难找到规律。第三，用 dig 你的域名 @114.114.114.114 查到的解析结果和实际配置不一致，同时用 DoH 查询的结果正常。这属于 DNS 层面的干扰，只换服务器 IP 无法解决。第四，每次修复都要人工改订阅，再通知用户更新，运维成本已经超过节点本身的成本。

到了这一步，继续批量买 IP 只是在重复消耗。更合理的做法是先停下来，按入口、中转、落地三层整理失效记录，确认问题属于架构层还是配置层。也要清楚一点：任何单一手段都不能承诺长期可用，只能降低失效频率，缩短恢复时间。

## 长期架构思路与高可用方案的适用边界

长期稳定的关键，是把入口、转发和后端解耦。用户订阅里填写的是入口池域名，不直接写某台服务器的 IP。入口层可以替换、可以批量部署。中转层负责线路选择和故障切换。落地后端不对公网暴露，这样能降低源站被关联、被连带失效的风险。在 XBoard 或 V2Board 中，可以按入口组来管理节点。某个入口失效时，只需替换这一层，后端和用户订阅都不受影响。配合健康检查和多线路，故障可以从全站中断缩小为局部切换。

Manguo Labs 的机场高可用入口解决方案主要面向以下几类场景：多个入口或中转频繁失效；换 IP 后短期内又反复出问题；需要区分入口、中转与落地故障，并设计切换方案。如果只是单个节点证书过期、端口写错或客户端配置有误，按前文步骤自行排查即可，不需要引入额外方案。

如果问题已经跨越单节点，可以先参考 https://manguolabs.com/node-firewall/ 了解规划和排查思路，再结合自己的规模评估是否需要。

## 常见问题

### 怎么快速判断节点是被墙还是配置错误？

同一节点分别在境内和境外各测一次。境外用 curl 或客户端能正常握手、境内超时或被重置，基本可判断为入口 IP/端口被封或被干扰；境内外都失败，优先查服务端进程、端口监听（ss -lntp）、证书是否过期，以及客户端里的 UUID、路径、SNI 是否和服务端一致。

### ping 不通但 TCP 能连，算被墙吗？

不一定。很多云厂商默认禁 ICMP，ping 不通不能单独作为证据。应该用 tcping 或 nc -vz 测目标端口，再用 openssl s_client -connect IP:443 -servername 域名 看 TLS 握手是否完成。端口能通但握手中断，更像 SNI 或特征层面的干扰。

### 换 IP 后很快又失效，是什么原因？

常见原因是入口和落地共用一台机器、源站 IP 通过域名解析或订阅泄露、同一段 IP 被批量标记，或者流量特征太集中。只换 IP 不改暴露面，新 IP 往往会沿着同样的路径再次暴露。更好的做法是把入口、中转、落地拆开，减少源站直接暴露。

### 有中转的线路要怎么定位是哪一段出了问题？

逐段测试：先从境内直连入口端口，再在入口机上测到中转的连通和延迟，最后在中转机上直接请求落地服务。哪一段开始超时或丢包，问题就在哪一段。转发日志里有大量 connection refused 指向落地，有 timeout 则多半是链路或封锁。

## 总结

处理墙常见问题，第一步是用境内外对照测试区分封锁、配置和网络故障；然后按 DNS、SNI/TLS、客户端、服务端单节点逐项检查，再按入口、中转、落地分段定位。换 IP、换端口只能临时恢复；如果反复失效，根因通常是源站暴露、入口单点或架构耦合，长期要靠入口、转发、后端解耦和多线路切换来降低影响，不存在一劳永逸的办法。
