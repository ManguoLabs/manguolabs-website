订阅泄露怎么办：先止损，再保留证据

发现订阅泄露后，处理顺序是：先保留证据，再重置订阅，然后观察旧链接是否仍被大量请求，最后决定是否限制账号。很多运营者第一反应是立刻封号或直接重置。这样能暂时止损，但会丢掉关键线索：泄露发生在什么时候、扩散到多少设备、是否和其他账号有关。

建议先把该用户最近 7 到 30 天的订阅请求记录、登录记录、流量曲线和节点连接日志导出或截图，再在 XBoard 后台为该用户重置订阅（更换 Token 与 UUID），并通知用户在自己的客户端重新导入。如果只是用户误把链接发到群里，重置后异常通常会明显回落；如果异常账号很快又出现同样的模式，就要考虑账号本身被共享或转售。

还要注意，单个 IP 数量偏多只是线索，不是结论。家庭宽带 NAT、移动网络切换、出差和一人多设备都会推高 IP 数。风险概率不是封禁的唯一依据，处置前应结合多维证据并经过人工复核。

异常现象与证据清单：看到什么才算可疑

判断订阅是否泄露，不要只看“IP 多不多”，而要看几类证据是否同时出现。常见信号有以下几种。第一，订阅拉取频率异常：正常客户端按更新间隔拉取，一天几次到几十次；如果同一 Token 每小时被几十个不同来源 IP 请求，更像链接被分发。第二，UA 杂乱：同一 Token 同时出现 Clash、Shadowrocket、sing-box、v2rayN 等多种客户端，且来自不同省份或运营商。第三，流量曲线突变：用量从每天几 GB 跳到几十 GB，并且在深夜持续高位。第四，节点侧同时在线：Soga 等后端记录到同一用户在同一时段从多个相距很远的真实 IP 建立连接。

可以按“看到 A → 判断 B → 下一步 C”处理：如果只有 IP 多、UA 单一且集中在同一城市，优先怀疑移动网络或 NAT，下一步联系用户确认设备情况；如果 IP 多、UA 多、地域分散，同时流量突增，判断为高度可疑，下一步保留证据并重置订阅；如果重置后旧 Token 仍被持续请求，说明链接已在外部流传，下一步需要追踪新 Token 是否再次扩散。

自助排查步骤：用访问日志和节点日志交叉验证

没有专门系统时，可以先用 Web 日志做低成本排查。以 Nginx 为例，操作步骤如下：

1）确定调查对象和时间窗，只用 Token 的前几位作为过滤条件，不要在工单或群聊里贴出完整链接。 2）统计订阅请求来源：grep "client/subscribe" /var/log/nginx/access.log | grep "token=前缀" | awk '{print $1}' | sort | uniq -c | sort -rn | head。 3）检查真实 IP 配置：如果站点套了 CDN，第一列可能都是 CDN 节点地址，需要先确认日志格式里记录了 CF-Connecting-IP 或 X-Forwarded-For，并设置 real_ip 相关指令，否则统计结果没有意义。 4）把订阅 IP 与 XBoard 的登录 IP、注册 IP 对比：登录 IP 和订阅 IP 完全不重合，且后者分布很广，是共享的典型特征。 5）到节点后端查看该用户的真实连接 IP，确认订阅拉取者是否真的在使用。 6）重置订阅后继续观察旧 Token：日志中旧链接仍有大量请求，且返回 403 或失败状态，说明外部仍在尝试使用。

这套方法适合排查单个账号；账号数量多、需要长期比对时，人工 grep 会很快失控。

重置 Token 后如何验证订阅泄露已止住

重置订阅 Token 只是第一步，还要用日志确认旧链接已失效、新链接没有再次外流。在 Nginx 访问日志中按订阅路径筛选请求，例如 grep "client/subscribe" access.log | awk '{print $1}' | sort | uniq -c | sort -rn，观察重置后来源 IP 的数量和分布。日志中的 Token 参数应脱敏后再做分析，不要把完整链接贴到工单或群聊里。

判断逻辑可以这样走：旧 Token 仍在持续请求，并且返回 403 或空订阅 → 说明泄露的链接仍在外部流转，但已经无法拿到节点，继续观察即可。新 Token 在一到两天内出现多个陌生网段、陌生 UA → 说明用户端或分享渠道仍在泄露，需要和用户沟通，再结合 Soga 的真实连接 IP 一起复核。如果站点前面有 CDN，要先确认 real_ip_header 和 set_real_ip_from 配置正确，否则日志里只会记录 CDN 节点的 IP，所有结论都会失真。

自助排查的失败边界与误判风险

单靠 IP 计数判断订阅泄露，最常见的问题是误判。下面几种情况都会让正常用户看起来像在共享订阅：

1. 校园网、公司网和运营商级 NAT 会让大量互不相关的用户共用一个出口 IP，形成“同 IP 多 Token”。 2. 移动网络切换基站，或者在 Wi-Fi 和 4G 之间来回切换，会让同一个 Token 在短时间内出现多个 IP。 3. 用户出差旅行、同时使用手机、电脑和路由器等多台设备，也会产生跨地区或多 UA 的请求。 4. 用户在本地套一层代理来拉取订阅时，订阅 IP 和实际连接 IP 本来就不一致。

因此，看到“同 Token 多 IP”，不能直接认定为共享。下一步要比对注册 IP、登录 IP、订阅 IP、UA 和 Soga 真实连接 IP 之间的历史关系：这些 IP 是长期稳定出现，还是突然冒出一批陌生网段。风险概率不是封禁唯一依据，高分账号应先限速、提醒或要求重置，再由人工复核后决定是否处理。

长期场景的审计架构与服务适用边界

如果订阅泄露反复出现，或者需要追查一个共享源头扩散出的多个账号，靠临时 grep 很难持续。长期方案一般有三个要点。第一，把审计数据写入独立的 MySQL，避免影响 XBoard 主库的性能。第二，长期保留 Token、登录、订阅请求和连接 IP 之间的历史关系，这样才能区分“老设备换了网络”和“新出现的陌生使用者”。第三，用仪表盘集中查看高风险账号，并保留人工复核记录，方便事后追溯每一次处理的依据。

什么时候这已经不是单点配置问题

少量账号手动重置、看日志通常就够了。如果单一 IP 线索已经不足以下结论，需要长期保存历史关系、持续调查共享账号并做人工复核，就可以考虑用一套成熟的审计方案来承接这些工作。

常见问题

重置订阅 Token 后，泄露问题就算解决了吗？

不一定。重置能让旧链接失效，但如果是用户主动转发，新链接还会被再次分享。重置后要观察 24–72 小时：新 Token 的订阅 IP 和 UA 如果很快又变多、又分散，就说明问题出在账号本身，需要人工复核和沟通。

同一个 Token 出现多个 IP，一定是共享吗？

不一定。手机在 Wi-Fi 和 4G/5G 之间切换、运营商 CGNAT、出差旅行、多台设备、客户端走代理更新订阅，都会产生多个 IP。还要看 IP 所在地区是否同时分散、UA 种类是否异常多、真实连接IP 是否在同一时间段并发出现，再下结论。

同一个 IP 下有多个 Token，说明什么？

可能是一个人有多个账号，也可能是公司、学校、宿舍或运营商 NAT 下的不同用户共用出口 IP。需要结合注册时间、支付记录、邀请关系和历史关系判断。只凭一个 IP 重合就关联或封禁账号，误伤风险很高。

账号关联追踪为什么要限制层数？

关联关系每多传播一层，证据就弱一些，层数越多越容易把无关用户牵连进来。比较稳妥的做法是设置上限，比如最多追踪 8 层，并且越往外的层权重越低，只用来提示人工复核，不作为直接处置的依据。

风险评分很高，可以直接封号吗？

不建议直接封号。风险概率不是封禁的唯一依据，应该先人工复核证据链，排除 NAT、移动网络、旅行和代理等情况。可以先限制设备数、重置 Token 或联系用户确认，留出申诉渠道，再决定是否进一步处理。

总结与下一步

订阅泄露的处理顺序：先重置 Token、留存日志止损，再用注册IP、登录IP、订阅IP、UA 和真实连接IP 做交叉判断，同时结合长期历史关系区分同 Token 多 IP 和同 IP 多 Token 的不同含义，关联追踪要限制层数。风险评分只用于排序和提示复核，不能作为封禁的唯一依据。NAT、移动网络、旅行、多设备和代理都是常见的误判来源。
