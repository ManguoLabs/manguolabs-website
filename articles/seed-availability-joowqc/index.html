节点打不开时先判断是不是“被墙”

很多人搜“墙教程”，实际想解决的是：机场节点突然连不上，到底是被墙了，还是自己配错了，下一步该做什么。直接判断方法是做双向对照：从国内网络和海外网络分别测试同一个 IP 和端口。国内不通、海外正常，大概率是封锁；两边都不通，优先查服务端进程、防火墙和配置；两边都通但客户端报错，多半是协议参数、证书或客户端本身的问题。

常见用户现象可以先粗分三类。第一类是全部节点同时超时，客户端日志出现 i/o timeout 或 context deadline exceeded，通常指向入口 IP 或端口层面的阻断。第二类是能建立 TCP 连接但很快断开，日志里有 connection reset by peer 或 tls handshake 失败，需要怀疑 SNI、TLS 指纹或证书。第三类是只有个别用户或个别地区失败，更可能是当地运营商线路、DNS 或客户端版本差异。先确定属于哪一类，再进入后面的分层排查，能少走很多弯路。

区分封锁、配置错误与普通网络故障

封锁、配置和网络问题的表现有时很像，判断时要看证据而不是凭感觉。可以按“看到 A → 判断 B → 下一步 C”的方式处理。看到国内 ping 和 tcping 全部失败、海外探测正常 → 判断入口 IP 可能被整体阻断 → 记录时间点，准备备用入口，不要反复重装服务端。看到 ICMP 正常但目标端口在国内超时、换端口后恢复 → 判断端口级干扰 → 检查该端口上的协议特征是否过于明显。看到 TCP 能连上但握手阶段被重置 → 判断可能与 SNI 或 TLS 特征有关 → 核对伪装域名、证书和指纹设置。

配置错误通常有更明确的服务端日志。Xray 或 V2Ray 日志中出现 invalid user，说明 UUID 或用户信息不一致；VMess 连接失败且服务器时间偏差较大时，要检查系统时间，偏差通常需控制在约 90 秒以内；证书过期则会在客户端看到证书校验类报错。普通网络故障则往往伴随丢包高、延迟抖动大，且海外探测同样不稳定，此时应先联系机房或换线路测试，而不是当作封锁处理。

单节点排查：DNS、SNI、TLS、客户端与服务端

确认问题集中在某个节点后，建议按固定顺序逐层排查，避免同时改多个参数导致无法定位：

1. 检查 DNS：分别执行 dig 节点域名 和 dig @8.8.8.8 节点域名，若国内解析结果与权威结果不同或指向异常地址，说明存在解析污染，可改用 IP 直连或可信 DoH 做对照。 2. 检查端口连通：国内与海外各执行一次 tcping 节点IP 端口，或 nc -vz 节点IP 端口，对比是否只有国内超时。 3. 检查 TLS 与 SNI：执行 openssl s_client -connect 节点IP:443 -servername 伪装域名，看证书链、有效期和域名是否匹配；若握手中途被重置，再换一个 SNI 做对照测试。 4. 检查服务端：用 systemctl status xray 确认进程存活，ss -tlnp 确认监听端口，再用 journalctl -u xray -n 100 查看最近日志，同时核对云厂商安全组与 ufw 或 iptables 规则。 5. 检查客户端：确认核心版本、系统时间、订阅是否已更新，并换一个客户端交叉验证。

每一步都记录结果，哪一层开始出现异常，问题就大概率在那一层。

修复后的验证：用分层探测确认问题真正消失

处理完不要只在自己电脑上测一次就结束。建议按“境外基线 → 国内多运营商 → 客户端实测”三步复核。第一步，在境外探针执行 curl -v --resolve sub.example.com:443:203.0.113.10 https://sub.example.com/，确认服务端本身正常。第二步，在国内电信、联通、移动各取至少一个测试点，执行 mtr -T -P 443 203.0.113.10 和 openssl s_client -connect 203.0.113.10:443 -servername sub.example.com。

判断逻辑如下： - TCP 握手超时，且 mtr 在出境段附近持续丢包，多半是入口 IP 被限制，下一步换入口或切换线路。 - TCP 能建立，但 TLS 握手后出现 connection reset by peer，偏向 SNI 或流量特征问题，下一步检查域名、证书与传输配置。 - 三网探测都正常，客户端日志仍是 i/o timeout，就回头查客户端系统时间、订阅版本和路由规则。

验证至少持续 24 到 72 小时，早晚高峰各测一次，并记录时间点，方便判断是否属于周期性失效。

失败边界：什么时候自助处理已经不划算

多数墙教程讲的是换 IP、换端口、改伪装域名。这些办法适合单个节点偶发失效，但有明确边界。出现以下信号时，说明问题已经超出单节点配置： - 换 IP 后几小时到几天内再次失效，而且在不同机房反复出现。 - 多个入口在同一时间段一起不可用。 - 中转机所在网段被整体限速或丢包。 - 旧订阅、面板域名的历史解析记录里还能查到落地或源站 IP。 对应的判断是：前两种往往不是“哪台机器坏了”，而是入口暴露方式和切换机制有缺陷，继续换 IP 只会消耗成本。第三种需要评估线路供应商本身，而不是继续调协议参数。第四种意味着后端已被关联，即使前端全部更换，也可能很快被定位。 另外，敏感时期整体网络质量下降，任何临时手段的效果都会明显打折。这时更现实的目标是缩短故障时间、保留可切换的备用路径，而不是追求某个节点一直可用。

长期架构与服务适用边界：入口、转发、后端解耦

长期思路是把链路拆成三层，并让每层可以单独替换： 1. 入口层：按运营商和地域分散部署多个入口，订阅域名与节点域名分开管理。 2. 转发层：负责线路选择和健康检查，探测到入口异常时调整下发策略。 3. 后端层：落地与源站只接受来自转发层的流量，不在任何公开解析或订阅中出现。 在 XBoard/V2Board 中，可以按节点分组下发不同入口，让单个入口失效时只影响一部分用户，并能较快切换。配置检查点包括：落地机防火墙是否只放行中转 IP；面板与订阅域名的 DNS 历史是否残留源站地址；健康检查间隔是否短于用户能明显感知的故障时长。 如果你已经遇到多入口或中转频繁失效、换 IP 后很快复发，或者需要设计入口、中转、落地的分层定位与切换方案，可以参考 Manguo Labs 的机场高可用入口解决方案：https://manguolabs.com/node-firewall/ 。它覆盖多线路与批量部署、降低源站暴露风险、客户端检查与故障排查。它的作用是降低被封锁后的影响面、缩短恢复时间，无法保证任何线路不被限制。单个节点配置错误按前文自查即可，不需要上整套架构。

什么时候这已经不是单点配置问题

如果按上面的步骤排查后发现，问题已经不在某个节点的配置上，而是多个入口或中转反复失效、换 IP 后很快又出现，那就是架构层面的问题了。这时可以参考成熟的高可用入口规划思路，把入口、中转、落地的故障界定清楚，再设计切换方案。

常见问题

怎么快速区分是被墙还是服务端挂了？

在服务器本机执行 ss -tlnp 确认端口在监听，再从境外 VPS 用 curl -v 或 openssl s_client 测握手。境外正常、境内多个运营商都超时或被重置，偏向封锁；境外也失败，先查服务进程、防火墙规则和证书是否过期。

只有 TCP 端口不通，ping 还能通，说明什么？

常见于针对端口或协议特征的干扰，IP 整体未必被封。可以先换端口或调整传输方式测试。如果 ping 和所有端口都不通，而境外探测正常，更接近 IP 级别封锁，这时换端口一般没用。

换 IP 后几天又失效，还要继续换吗？

短期内可以换 IP 恢复服务，但反复失效通常说明源站或入口暴露方式本身有问题，比如真实 IP 直接写在订阅里、多个节点共用特征明显的配置。继续换只会提高成本，建议排查暴露路径，再考虑入口、中转、落地分层。

中转线路出问题时，用户端会看到什么？

典型表现是同一入口下的多个落地节点同时变慢或超时，而直连落地测试正常。这时问题在入口到中转或中转到落地这一段，按段测延迟和丢包（如 mtr）就能定位，不应先去改落地节点配置。

总结与下一步

本墙教程的核心是先判断再动手：用境外和境内多网络对照测试区分封锁、配置和网络问题；按 DNS、SNI、TLS、客户端、服务端的顺序排查单节点；再把链路拆成入口、中转、落地逐段定位。换 IP、换端口只是临时手段，有明确的适用边界。如果失效反复出现，就需要把入口、转发和后端解耦，减少源站暴露，并设计多线路切换。
