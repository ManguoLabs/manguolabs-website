用户现象与直接判断

搜索“墙哪个好”的人，多数想问的是：哪种机场或线路方案在封锁环境下更稳定、更不容易整体失联。简短回答是，没有哪个协议或哪家服务能在任何时段都稳定可用。稳不稳主要看可用性设计：入口是否分散，失效后能否快速切换，源站是否暴露，以及出问题时能否分清是入口、中转还是落地的故障。只比较协议名称或单个节点的测速，很难得出可靠结论。

常见现象可以先粗分为三类。第一类是全部节点同时超时，但换一张手机卡或换一个运营商网络就恢复，这通常和入口 IP 或端口被干扰有关。第二类是只有某个节点打不开，其他节点正常，更像单节点配置或服务端进程问题。第三类是能连上但很慢、频繁断流，需要结合时段和线路判断是不是拥塞。先确认自己属于哪一类，再决定排查顺序，比反复更换客户端更省时间。

区分封锁、配置与网络问题

判断时建议按“看到 A → 判断 B → 下一步 C”的方式推进。看到入口 IP 在国内 ping 和 TCP 443 都不通，但从海外探测正常，可以判断入口被阻断的可能性较大，下一步换备用入口验证，不要先改服务端配置。看到 TCP 端口能连通，但 TLS 握手失败或客户端日志出现 handshake timeout，可以判断是 SNI、证书或协议特征层面的问题，下一步核对证书域名和 servername 是否一致。看到海外和国内都连不上，就要怀疑服务端进程、防火墙规则或机器本身，下一步登录服务器检查。

纯配置错误也有比较固定的表现：UUID、密码或路径写错时，TCP 和 TLS 通常都正常，但代理层鉴权失败，服务端日志会出现 invalid user、rejected 等记录。网络拥塞则多数表现为晚高峰丢包率升高、白天恢复，延迟曲线有规律。三类问题的处理方式差别很大：封锁要换入口或调整架构，配置错误改参数即可，拥塞则需要换线路或增加中转。

DNS / SNI / TLS / 客户端 / 服务端单节点排查

针对单个节点，可以按下面的顺序逐层排查。第一步查 DNS：执行 dig node.example.com 或 nslookup，确认解析出的 IP 和预期一致，没有被污染成无关地址。第二步查 TCP：用 nc -vz IP 443 或 tcping 测试端口，不通时同时从海外机器测一次，用来区分阻断和宕机。第三步查 TLS 与 SNI：执行 openssl s_client -connect IP:443 -servername node.example.com，确认证书链完整、域名匹配、没有过期。第四步查客户端：核对协议、端口、传输方式、路径与服务端是否一致，并打开客户端日志看具体报错。第五步查服务端：用 systemctl status 和 journalctl -u 服务名查看进程状态和日志，用 ss -tlnp 确认端口已监听，再检查 iptables、ufw 或云厂商安全组是否放行。

这一套流程能覆盖大部分单节点故障。如果五步都正常，但国内仍间歇性连不上，问题就不在这台机器的配置上，需要往入口、中转、落地的分层结构去找原因。

修复后的覆盖验证：别只看一次能连上

很多人问“墙哪个好”，其实是在问哪条线路恢复后能稳定使用。验证时不要只在自己电脑上点一次测速，建议按三步做。 第一步，在至少两个不同运营商的探测点执行 curl -v --resolve 域名:443:入口IP https://域名/。如果 TLS 握手完成并返回预期状态码，说明入口和证书正常。如果卡在 Client Hello 之后超时，优先怀疑 SNI 或入口 IP 被干扰。 第二步，用 openssl s_client -connect 入口IP:443 -servername 域名 核对证书链与 SNI 是否一致。再用 mtr -T -P 443 入口IP 看丢包出现在哪一跳。丢包集中在跨境段、落地直连却正常，说明问题在入口或中转，下一步应查中转，而不是改客户端。 第三步，在 Clash 或 sing-box 日志里确认 dial 目标、超时类型和重试次数，分清 i/o timeout、connection reset 和 TLS handshake error。验证周期至少覆盖一次晚高峰和次日同一时段，并记录每个入口的可用时长。多地域、多时段结果一致，才算真正恢复。

临时处理的失败边界：换 IP 为什么撑不久

换 IP、换端口、改 SNI、切换备用中转，本质都是止血手段，适合单节点故障时快速恢复访问。出现以下信号时，说明已经超出临时处理能解决的范围： - 新 IP 上线几小时到几天内，再次出现握手超时； - 多个入口同时失效，但落地机直连正常； - 同一订阅里的节点在相近时间集体变红； - 每次更换都要手动改订阅，再等用户刷新。

这些现象通常指向同一个根因：入口地址和后端强绑定，源站或中转 IP 直接暴露在订阅和客户端配置里。地址一旦被识别，更换的只是表面地址，暴露路径没有变。继续堆 IP 只会增加成本和运维压力。

另外，客户端侧的问题换服务端也解决不了，应先排除。常见的有规则写错、系统时间偏差导致 TLS 失败、本地 DNS 被污染。任何方案都无法保证线路完全不受干扰，合理的目标是缩短故障发现和切换的时间。

什么时候这已经不是单点配置问题

如果按文中步骤排查后，问题只出在单个节点，自行修复通常就够了。如果多个入口或中转反复失效，或者换 IP 后很快又出现同样的问题，说明问题已经不在单个节点，而在整体架构，这时再考虑做系统的高可用规划。

常见问题

怎么判断节点是被墙，还是配置写错了？

先用境外机器测试同一节点：境外能连、国内多个运营商都连不上，大概率是封锁；境内外都连不上，就先查服务端进程、端口监听（ss -lntp）、证书和客户端里的 UUID、SNI、传输方式。如果 ping 不通但 TCP 443 能连通，不能直接判断为被墙，因为不少机器本来就禁 ICMP。

只封端口和封整个 IP 有什么区别？

在国内用 nc -vz 或 tcping 测试同一 IP 的多个端口：只有原端口超时、其他端口正常，多半是端口级封锁，换端口可以临时恢复；所有端口都超时，但境外测试正常，更像是整个 IP 被封，需要换入口 IP。不论哪种情况，都应记录发生时间和协议，方便之后对比规律。

换了 IP 没几天又被墙，是 IP 质量差吗？

不一定。如果新 IP 很快失效，更常见的原因是订阅泄露、入口与源站共用同一 IP、协议特征明显，或者流量过于集中在单个入口。只换 IP 而不改变这些条件，问题通常会反复出现。应该检查订阅分发方式、源站是否暴露，以及是否有多个入口分摊流量。

中转线路一定比直连更不容易被墙吗？

不一定。中转能把落地 IP 藏在后面，降低源站暴露风险，但中转入口本身仍可能被封。中转的价值在于入口坏了只需替换入口层，落地和后端配置可以不动，前提是入口、转发和后端之间做了解耦，并且设计了切换方式。

总结与下一步

“墙哪个好”没有通用答案。正确的顺序是：先用境内外对照测试，区分封锁、配置和网络问题；再按 DNS、SNI、TLS、客户端、服务端逐项检查单个节点；然后按入口、中转、落地分层定位。换端口、换 IP 可以作为临时处理，但如果多个入口反复失效，就应该解耦入口、转发和后端，并配合多线路和切换方案，降低单点失效的影响。
