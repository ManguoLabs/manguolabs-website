防墙教程先解决什么：用户反馈“连不上”时的直接判断

大多数机场运营者搜索防墙教程，起因是用户集中反馈“节点超时”“能连但打不开网页”“白天正常、晚上全挂”。先给结论：网上流传的“换端口、换协议、套 CDN”只能处理一部分情况。第一步应判断问题属于封锁、配置错误还是网络质量，再按入口、中转、落地逐层定位。没有定位就换 IP，往往换完几天又出现同样现象，还会让更多源站地址暴露。

现象可以先粗分三类。所有地区、所有运营商同时完全不通，而服务器本机进程正常，优先怀疑入口 IP 或端口被阻断。只有某个运营商或某个时段异常，多半是线路拥塞或路由绕行。只有部分客户端失败，多与客户端版本或订阅参数有关。这一步只需要收集三项信息：故障时间、用户运营商与地区、客户端名称和版本。掌握这些信息后，后面的排查才有比较对象。

区分封锁、配置与网络问题：看到什么，判断什么

三类问题的表现有交叉，建议按“看到 A → 判断 B → 下一步 C”的方式处理，不要凭感觉下结论。

看到国内多地 ping 和 TCP 443 全部超时，境外探测点却正常，服务器上 ss -tlnp 显示端口仍在监听，判断为入口 IP 层阻断的可能性较高，下一步用同机房另一个 IP 做对照测试。看到 TCP 能建立连接，但 TLS 握手后很快被重置，换一个 SNI 或换端口后恢复，判断为针对域名或流量特征的干扰，下一步检查 SNI 与证书。看到所有地区都失败，且服务端日志出现 uuid 不匹配、证书过期或 REALITY 校验失败，基本可以判断为配置问题，与封锁无关，下一步回滚最近的配置改动。看到只有晚高峰丢包严重、延迟暴涨，mtr 显示在某一跳之后开始大量丢包，判断为线路质量问题，下一步考虑更换中转线路，不需要换入口 IP。

这一步分清问题类型，可以少做很多无效的换 IP 操作。

单节点排查步骤：DNS、SNI、TLS、客户端与服务端

按从外到内的顺序逐层验证，每一步只改动一个变量： 1. DNS：在国内机器执行 dig entry.example.com +short，与境外解析结果对比。返回异常 IP 或记录与预期不一致，说明解析被污染或记录未生效，可以先用 IP 直连测试。 2. 端口：执行 nc -zv 入口IP 443，或用 tcping 检测。全部超时，而服务端本机监听正常，问题偏向 IP 层或线路阻断。 3. SNI 与 TLS：执行 openssl s_client -connect 入口IP:443 -servername 你的域名。握手阶段被 reset 或卡住，而换一个 SNI 后正常，问题集中在域名特征上。如果报 certificate verify failed，则属于证书配置问题。 4. 服务端：执行 journalctl -u xray -n 100 查看最近日志。出现 invalid user、rejected 等记录时，回到客户端核对参数。 5. 客户端：升级内核版本，导出完整配置，与服务端逐项比对 UUID、flow、fingerprint、path。

五步走完仍无法定位，再进入入口、中转、落地的分层排查。

修复后的覆盖验证：分地域、分运营商、分客户端复测

防墙教程里的任何调整，都要用覆盖验证收尾。一台测试机能连通，只能说明这一条路径正常。建议至少准备三类视角：国内电信、联通、移动各一个探测点，一台境外对照机，以及 Clash Meta、sing-box、v2rayN 等主流客户端。 复测按层进行。先用 dig 入口域名 @223.5.5.5 和 dig 入口域名 @8.8.8.8 对比解析结果。再用 curl -v --resolve 入口域名:443:入口IP https://入口域名 确认 TCP 与 TLS 握手。然后用 openssl s_client -connect 入口IP:443 -servername 入口域名 核对证书链和 SNI，最后用 mtr -T -P 443 入口IP 观察丢包出现在哪一跳。 判断时可以按这几条走： 1. 只有某一家运营商超时，境外对照机正常，优先怀疑该线路被干扰或质量劣化，下一步看是否需要切换入口或调整线路。 2. 所有探测点都握手失败，先回头检查证书和服务端配置。 3. 握手成功但客户端报 context deadline exceeded，再检查中转到落地这一段。

复测结果建议按时间记录，方便和下一次失效做对比。

失败边界：自助排查到哪里就该停下

自助处理能解决的，主要是配置类问题，例如证书过期、SNI 与域名不一致、端口未放行、客户端核心版本过旧。对于封锁类问题，自助手段只能临时缓解，比如更换入口 IP、调整端口、改用其他传输方式。即使暂时恢复，也不代表问题已经消失。 出现以下信号时，说明问题已经超出单节点排查的范围： - 换 IP 后几天内同一入口再次失效。 - 多个入口在相近时间段集中出现异常。 - 中转正常，但部分落地间歇性断流。 - 每次恢复都依赖人工逐台登录服务器修改。 这时继续反复换 IP，成本会越来越高。频繁变更还可能让新地址更快被关联识别。另外，源站 IP 一旦被订阅、面板回调或日志泄露出去，前端换多少入口都意义有限。 正确的下一步是停止零散修补，先梳理三件事：入口、中转、落地之间的依赖关系；源站究竟在哪些地方暴露；切换动作能否标准化。要承认，任何方案都只能降低失效频率和恢复耗时，无法让节点不再受到干扰。

长期架构思路与 Manguo Labs 方案的适用边界

长期稳定的核心是解耦，也就是让入口层、转发层和后端落地各自可替换。 具体可以从三层入手： 1. 入口层准备多条线路和多个可切换地址，由订阅或 DNS 统一下发，单个入口失效时只需替换这一层。 2. 中转层负责路由选择和分流，不直接暴露源站。 3. 落地层只接受来自中转的流量，并对外隐藏真实地址。 配合 XBoard/V2Board 面板管理节点，再加上批量部署脚本，换线时就能做到改配置、批量下发、复测确认这样的流程化操作，不必逐台手工处理。 Manguo Labs 的机场高可用入口解决方案面向的正是这类场景：多个入口或中转频繁失效、换 IP 后短期内反复出现，或需要区分入口、中转与落地故障并设计切换方案。方案内容包括高可用规划、降低源站暴露风险、多线路与批量部署，以及客户端检查与故障排查。 如果你的问题只是单台节点的证书或端口配置错误，按前文步骤自查通常就够了。如果问题跨越多层并且反复出现，可以先到 https://manguolabs.com/node-firewall/ 了解方案细节，或通过 https://t.me/ManguoShop_bot 说明现有架构后再做评估。

什么时候这已经不是单点配置问题

做完上面的自助排查后，如果问题只出在某一个节点的配置上，修正后通常就能恢复。但如果多个入口轮流失效、换 IP 后很快复发，说明问题出在架构上，就需要从入口、转发、后端解耦的角度重新规划。

常见问题

怎么快速判断节点是被墙还是配置错误？

国内探测点 ping 和 tcping 都不通，海外探测点却正常，大概率是 IP 或端口被封锁。如果国内外都连不上，或者 TCP 能通但 TLS 握手失败、服务端日志报 UUID 或认证错误，就先查配置、证书和服务进程。

只封了端口，换端口能解决吗？

同一个 IP 上其他端口还能 tcping 通的话，换端口往往能临时恢复。但如果流量特征和入口暴露方式没变，新端口可能很快再次失效。换端口只是临时手段，最好同时检查协议特征和入口分布。

为什么换了 IP 没几天又失效？

常见原因有几种：入口和源站是同一台机器，换 IP 后地址很快又暴露；订阅里长期写死同一批地址；协议或 SNI 配置特征明显。只换 IP 不改结构，问题会反复出现。

中转和落地哪个出问题更常见？怎么区分？

在中转机上直接 curl 或 tcping 落地端口。能通，说明问题在用户到入口或入口到中转这一段；不通，就查落地防火墙、服务进程和中转出口线路。分段测试比凭经验猜可靠。

什么时候需要考虑高可用入口方案？

多个入口或中转经常失效、换 IP 后短期内又出问题，或者你需要明确区分入口、中转、落地故障并设计自动或手动切换时，就该考虑了。这时已经超出单节点配置的范围，需要做架构上的规划。

总结与下一步

防墙的核心不是靠某个参数一劳永逸，而是先准确判断问题：国内外对比测试区分封锁与配置问题，按 DNS、SNI、TLS、客户端、服务端逐项检查单节点，再按入口、中转、落地分段定位。换 IP、换端口只是临时手段，有明确的边界。失效反复出现时，应把入口、转发和后端解耦，降低源站暴露风险，并准备多线路切换。
