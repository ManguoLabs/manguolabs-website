防墙如何解决：机场节点被墙的判断、排查与高可用入口思路

防墙如何解决：先判断是不是真的被墙

防墙不能只靠一句“换 IP”或“换协议”。对机场运营者来说，可行的路径分四步。先确认节点是被封锁、配置出错，还是普通网络波动。确认是封锁后，再区分被干扰的是 IP 层、端口层还是 TLS/SNI 层。短期内用更换入口、端口或增加中转来恢复服务。长期则把入口、转发和后端落地拆开，任何一层失效都能单独替换，同时不暴露源站。

用户反馈的现象常见四类。第一类是大量用户同时报告超时，但海外检测节点正常。第二类是部分省份或运营商不通，其他地区可用。第三类是能连上但速度骤降、丢包明显。第四类是同一台机器换新 IP 后几天又失效。前两类多指向入口被阻断或限速，第三类可能是 QoS 或线路拥塞，第四类说明问题不在单个 IP，而在暴露方式或架构本身。直接判断的原则是：国内不通而海外通，优先怀疑封锁；国内外都不通，先查服务端。

区分封锁、配置与网络问题

三类问题表面上都是“连不上”，但证据不同。配置问题通常是全局性的：任何地区、任何网络都失败，服务端日志里有握手失败、UUID 不匹配或证书错误；如果是刚改过配置、升级内核或面板后出现，可以先回滚。网络问题多为波动性：mtr 显示某一跳持续丢包，晚高峰加剧、凌晨恢复，换一条国际出口就好转。封锁则有选择性：国内到该 IP 的 ICMP 和 TCP 全部超时，从海外 VPS 连接却一切正常；或者 TCP 端口能通，TLS 握手却在 Client Hello 之后被重置。

可以按“看到 A → 判断 B → 下一步 C”快速分流： - 海外和国内都超时 → 服务端或配置故障 → 查进程、端口监听和日志。 - 国内全端口超时、海外正常 → IP 被阻断 → 不要在该 IP 上反复调试，准备替换入口。 - TCP 通但 TLS 被 RST → SNI 或流量特征被识别 → 检查 SNI、证书与伪装配置。 - 丢包有明显时段规律 → 线路质量问题 → 优化线路或增加中转。

DNS / SNI / TLS / 客户端 / 服务端单节点排查

单节点排查建议从外到内按顺序进行，每一步只验证一个变量。同时改动多处会导致无法定位问题出在哪里。

1）DNS：在国内机器执行 dig node.example.com，再对比 dig @1.1.1.1 node.example.com 的结果。如果国内返回的 IP 异常或无结果，说明可能存在污染，可先让客户端直接填 IP 验证。 2）TCP 端口：用 nc -vz 203.0.113.10 443 分别从国内和海外测试。国内超时而海外成功，即为入口层阻断。 3）TLS 与 SNI：执行 openssl s_client -connect 203.0.113.10:443 -servername www.example.com。如果出现 connection reset 或 unexpected eof，而换一个 SNI 后能完成握手，说明 SNI 层被干扰。 4）客户端：确认内核版本、系统时间和订阅都是最新的。时间偏差过大会导致部分协议鉴权失败。 5）服务端：用 ss -tlnp 确认端口在监听，再用 journalctl -u xray -n 100 查看入站记录。如果国内发起连接时日志里完全没有记录，说明流量根本没有到达服务器。

走完这五步，通常能把问题落到某一处，再决定是否需要做入口、中转、落地的分层定位。

处理后的覆盖验证：分层确认是否真正恢复

换 IP、改端口或调整 SNI 之后，不能只凭一台测试机“能连上”就判定防墙问题已解决，需要按层复核。第一步，在境内电信、联通、移动各取至少一个探测点，执行 nc -vz 入口IP 443，确认 TCP 握手能完成。第二步，执行 openssl s_client -connect 入口IP:443 -servername 你的SNI，确认证书链和 SNI 与配置一致，没有出现握手中断。第三步，用客户端分别连接入口直连、经中转和直达落地三种路径，用 curl -I https://www.google.com 的耗时做对比。

判断逻辑如下： - 握手通、TLS 失败：先查证书和 SNI，再查中间设备干扰。 - TLS 正常但客户端超时：回到客户端核对协议参数和 UUID 是否一致。 - 三网中只有一网异常：更可能是该运营商线路质量问题，与封锁关系不大。

验证要持续 24 至 72 小时，并记录每次失败的时间点和运营商。如果短时间内恢复后又整批失效，说明这次处理只覆盖了表象。

失败边界：临时手段在什么情况下不再有效

换 IP、换端口、换域名都属于低成本的临时处理，适合解决单个入口被识别或误伤的情况，但有明确的边界。

常见信号和对应判断： - 新 IP 上线几小时到几天后再次失效，且多个入口先后出现同样情况：通常不是 IP 本身的问题，而是入口地址通过订阅、面板或公开配置被批量收集，或者协议特征和流量模式容易被识别。 - 多个入口同时异常，但它们共用同一个落地：应先排查落地服务端、证书到期或后端进程，而不是继续换入口。 - 某个中转出现丢包后，下游所有节点都不稳定：说明中转是单点，替换入口无法解决。 - 日志里频繁出现 connection reset 或 TLS handshake timeout，且集中在特定时段：要把它和运营商晚高峰拥塞区分开，因为两者的处理方式完全不同。

一旦出现“越换越快失效”的趋势，继续手工替换只会推高成本和维护压力。这时应停止零散修补，转向架构层面的调整。

长期架构与服务适用边界

长期思路是把入口、转发、后端拆开。 - **入口层**：使用可替换的入口池，按地区和运营商分组。订阅只下发当前分组可用的入口，减少整体暴露面。 - **转发层**：承担线路优化和故障切换，中转之间互为备份，避免单点。 - **后端层**：落地和源站不直接对用户公开，降低源站暴露风险。 在 XBoard/V2Board 中，可以按节点分组和权限控制下发入口，并配合健康检查自动下线异常入口。批量部署时，使用统一的配置模板，并在模板中固定证书、SNI 和端口的检查项。 如果你遇到以下情况，可以评估 Manguo Labs 的机场高可用入口解决方案： - 多个入口或中转频繁失效； - 换 IP 后短期内反复出现同样问题； - 需要明确区分入口、中转与落地故障，并设计切换方案。 这套方案提供多线路规划、客户端检查和故障排查，但它降低的是失效概率和恢复时间，不能消除所有风险。单个节点的配置错误，按前文的步骤通常可以自行解决，不需要引入额外方案。方案说明见 https://manguolabs.com/node-firewall/，也可以通过 Telegram 沟通现有架构情况。

什么时候这已经不是单点配置问题

如果已经按本文步骤排查过单节点，入口仍然一个接一个失效、换了 IP 很快又断，问题通常出在架构层，而不是某个配置项。这时可以先整理现有链路结构和故障记录，再评估是否需要做入口与后端解耦的高可用改造。

常见问题

节点连不上，怎么判断是被墙还是配置错了？

从境外 VPS 对该 IP:端口做 TCP 连接和 TLS 握手测试。境外能通、国内多地 tcping 都不通，大概率是 IP 被封锁。境外也不通，就先查服务端进程、端口监听（ss -lntp）、防火墙规则和证书是否过期。只有部分运营商不通，更像线路或 QoS 问题。

换 IP 后几天又被封，是什么原因？

常见原因有三个：源站 IP 直接写在订阅里，协议特征或 SNI 配置固定且容易识别，流量集中在单个入口。只换 IP、不缩小暴露面，新 IP 很可能重蹈覆辙。应同时检查订阅下发的内容，以及入口与落地是否耦合在一起。

只封了端口还是整个 IP，怎么区分？

在国内对同一 IP 测试多个端口，例如 22、443 和业务端口。只有业务端口不通、其他端口正常，多为端口级封锁，换端口可以临时恢复。所有端口都不通且 ICMP 也丢失，多为 IP 级封锁，需要更换入口 IP。

加中转就能防墙吗？

中转可以把落地 IP 藏在后面，降低源站暴露，但中转入口本身仍可能被封。它的价值在于入口失效时只换入口、不动落地。前提是有多个入口和可切换的订阅机制，否则只是把单点从落地挪到了中转。

总结与下一步

防墙如何解决，重点不是找一个不会被识别的协议，而是让故障可判断、可定位、可切换。具体做法：用境内外对比测试区分封锁、配置和网络问题；按 DNS、SNI、TLS、客户端、服务端逐项排查单节点；再按入口、中转、落地分层定位。换端口、换 IP 只能临时止血。如果反复失效，就要把入口、转发和后端解耦，并配合订阅侧的快速切换，缩短整体中断时间。
