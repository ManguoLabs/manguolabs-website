内鬼误判的直接答案：先看异常现象与证据清单

内鬼误判，是指把正常用户当成泄露或转卖订阅的“内鬼”来处理。结论很直接：仅凭“同一 Token 出现多个 IP”不能认定共享。订阅请求、登录记录和节点真实连接必须放在同一条时间线上交叉印证，而且风险概率不是封禁唯一依据。多数误判来自只看面板在线 IP 数或一次订阅日志，就直接重置 Token 或封号。

常见异常现象有四类：短时间内订阅地址被多个城市的 IP 拉取；UA 从一种客户端突然变成多种；节点侧同时在线 IP 超过套餐设备数；用户工单反映流量莫名用完。动手处理前，先整理一份证据清单，至少包括：可疑 Token 对应的用户 ID 与套餐，最近 7 到 30 天的订阅请求（时间、IP、UA），面板登录 IP，注册 IP，节点上报的在线 IP 及时间段，以及流量曲线。缺少其中任何一类证据，结论只能写“待观察”，不能写“已确认”。

Token、注册IP、登录IP、订阅IP、UA、Soga真实连接IP各说明什么

Token 是订阅凭证，泄露后任何人都能拉取。它关联的 IP 最能反映扩散范围，但也最容易被 CDN 地址污染。注册 IP 和登录 IP 代表账号所有者操作面板的位置，可以作为“本人基线”。订阅 IP 是客户端请求 /api/v1/client/subscribe?token=*** 时的出口地址。如果站点套了 Cloudflare，却没有配置 set_real_ip_from 和 real_ip_header CF-Connecting-IP，日志里记录的全是 CDN 节点 IP，看起来就像“同 Token 多 IP”。

UA 能区分设备类型，例如 ClashMetaForAndroid、clash-verge、Shadowrocket，但 UA 可以伪造，只能作辅助证据。Soga 真实连接 IP 是节点后端上报的实际代理连接来源，最接近“谁在消耗流量”。判断原则如下： 订阅 IP 多而连接 IP 少，往往只是更新频繁或切换网络。 订阅 IP 与连接 IP 都分散在互不相邻的地区，且使用时间重叠，才算共享的较强信号。

认定内鬼前的可执行复核步骤

1. 校准数据源。先确认 Nginx 日志记录的是真实 IP，可执行： grep "client/subscribe" /var/log/nginx/access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head 如果排在前面的多是 104.16.0.0/13、172.64.0.0/13 这类 CDN 网段，先修正配置，再做判断。 2. 按 Token 拉出时间线，把订阅、登录、连接三类记录按分钟合并。 3. 检查时间重叠。看到同一时段两个相距很远的连接 IP 同时有流量，可初步判断存在共享可能。下一步核对两者是否属于同一运营商 ASN，以及用户是否开启了代理或机场中转。 4. 统计 UA 种类，确认是否超出套餐设备数的合理范围。 5. 对照本人基线。如果登录 IP 与连接 IP 同城且同运营商，多半是多设备使用或移动网络切换。

6. 对结论分级：疑似、待观察、高风险。只有高风险才进入人工复核并联系用户，不直接封禁。整个过程保留原始日志截图，方便事后申诉核对。

处置前的覆盖验证：确认证据链没有缺口

给账号贴上“内鬼”或“共享”标签之前，先确认证据覆盖了完整链路，不能只看订阅日志里出现了几个 IP。建议按三步核对。

第一，确认同一时间窗口内既有订阅拉取记录，也有 Soga 上报的真实连接 IP。只有订阅请求而没有连接记录，可能只是客户端定时刷新，也可能是反代导致来源地址失真。第二，检查 Nginx 或 CDN 是否正确透传 X-Forwarded-For。如果日志里大量出现同一个回源 IP，说明采集层本身有问题。第三，对比注册 IP、登录 IP 与订阅 IP 的历史关系，看新 IP 是否与旧 IP 属于同一运营商或同一地区网段。

判断时可以按下面的逻辑走。看到同 Token 多 IP，但 UA 一致、连接时段不重叠，更可能是用户换网或移动网络切换，下一步应延长观察窗口，而不是立即重置。看到多个不同 UA 在同一时段并发连接，且这些 IP 又关联到其他 Token，才进入人工复核队列。

失败边界：哪些情况下证据无法下结论

有些场景下，再完整的日志也只能给出“可疑”，给不出“确定”。运营商级 NAT 会让成百上千个用户共用少量出口 IP，同 IP 多 Token 在这类网段里很常见。学校、公司和酒店网络同理。移动网络的地址池轮换频繁，IPv6 隐私地址也会定期变化，单个用户一天内出现十几个 IP 并不罕见。用户出差或旅行时，IP 归属地会短时间跨城市甚至跨国。还有一些用户先挂其他代理再拉取订阅，这时订阅 IP 只是代理出口，与本人无关。

另外，如果日志保留周期很短，或者中途改过反代结构，历史关系就会断档，传播追踪得出的关联也会偏弱。遇到这些情况，应把结论降级为“待观察”，并记录不确定的原因。

需要强调的是，风险概率不是封禁唯一依据。它只是排序和分流的工具。真正处置前，应结合用户沟通、套餐规则和人工复核结果，并给账号留出申诉与解释的空间。

长期架构思路与服务适用边界

如果用户规模不大、可疑案例偶发，用 grep 过滤订阅日志、配合 SQL 查询 v2_user 与登录记录，通常已经够用。问题在于规模扩大以后，分散查询很难保留长期历史关系，误判也更难回溯。比较稳妥的长期做法有三点。一是把审计数据写入独立 MySQL，避免高频关联查询拖慢 XBoard 主库。二是把 Token、登录、订阅、UA 与真实连接 IP 统一按时间轴归档，账号关联只沿高置信度的边传播，层数越深权重越低。三是在仪表盘里把高风险账号推入人工复核，并记录每次判断的理由。

当单一 IP 线索已经不足以判断，又需要持续调查订阅共享或可疑账号时，可以参考 Manguo Labs 的 XBoard 订阅安全审计系统（https://manguolabs.com/xboard-security-audit/）。它的定位是做证据关联和辅助复核，用来降低 NAT、移动网络和多设备场景下的误判，并不替代运营者自己的处置判断。需求细节和兼容性也可以先通过 Telegram 沟通确认。

什么时候这已经不是单点配置问题

用户量小时，手工导出日志、写 SQL 对照基本够用。当单一 IP 线索已经不足以判断，需要长期保存历史关系、把订阅 IP 和真实连接 IP 关联起来，并且持续复核可疑账号时，可以考虑用专门的审计系统来承接这些证据，最终处理仍由人工决定。

常见问题

同一个 Token 一天出现 5 个 IP，是不是一定在共享订阅？

不一定。手机在 Wi-Fi 和 4G/5G 之间切换、出差旅行、多台设备，或者用户自己挂了代理再拉订阅，都会让 IP 数量变多。建议先看这些 IP 是否集中在同一地区或同一运营商，UA 是否稳定，Soga 真实连接 IP 是否和订阅 IP 一致，再决定要不要进入人工复核。

同一个 IP 下有多个账号，能直接判定是内鬼吗？

不能。校园网、公司出口、运营商 CGNAT 和公共 Wi-Fi 都会让很多人共用一个公网 IP。还要看这些账号的注册时间、邀请关系、UA 指纹、登录时间段是否高度重合，以及这种关系是长期存在还是偶尔出现。

为什么要看 Soga 真实连接 IP，订阅 IP 不够吗？

订阅 IP 只记录谁拉取了配置，真实使用节点的设备可能是另一台。Soga 侧的连接 IP 反映实际在用节点的来源。两者长期对不上，而且连接 IP 分散在多个地区，比单看订阅 IP 更有参考价值，但仍然要排除代理和中转的影响。

风险评分很高，可以自动封禁吗？

不建议。风险概率不是封禁的唯一依据，它的作用是排定复核顺序。比较稳妥的流程是：高分先限制或提醒，人工核对证据链，必要时联系用户说明情况，确认之后再处理，并保留证据记录方便申诉复查。

账号关联追踪为什么要限制层数？

关联关系每多传一层，误伤的可能就越大，因为共享网络会把无关账号串起来。分层追踪（例如最多 8 层）方便看清传播路径，但越往外层的账号越需要独立证据，不能因为“和可疑账号有关联”就一起处理。

总结与下一步

避免内鬼误判，关键是不让单一指标直接定案。先整理异常现象和证据清单，把 Token、注册/登录/订阅 IP、UA、Soga 真实连接 IP 按时间线对齐，借助长期历史关系区分偶发和持续异常。同 Token 多 IP、同 IP 多 Token 都要先排除 NAT、移动网络、旅行、多设备和代理这些原因。账号关联可以分层追踪，风险评分只用来决定复核顺序，最终处理要经过人工复核，并保留证据。
