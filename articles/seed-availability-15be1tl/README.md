# 墙对比怎么做：用墙内外测试判断节点是被封、配置错误还是线路故障

关键词：墙对比、节点被墙判断、墙内外连通性对比、入口中转落地排查、机场高可用入口

墙对比就是让同一个节点在墙内、墙外各测一次：墙外 TCP 和 TLS 都正常，墙内只有 ICMP 能通、TCP 超时或握手被重置，大概率是封锁；墙内外都失败，先查服务端配置、证书和进程；只有部分地区或运营商失败，更像线路或路由问题。先分清是哪类问题，再决定是换 IP、改配置，还是调整入口架构。

## 节点连不上时先做墙对比：一句话判断方向

“墙对比”的做法是：用同一个节点、同一份配置，分别从国内网络和境外网络发起连接测试，然后对比结果。境外能连、国内不通，基本指向入口 IP 或端口在国内链路上受到干扰。两边都不通，问题多半在服务端进程、配置或防火墙。两边都能连上，但客户端仍然报错，就优先检查客户端配置、订阅内容和本地网络。

现象可以先粗分三类。第一类，国内 ping 不通而境外正常，多为 IP 层封锁。第二类，ping 能通但 TCP 端口超时，可能是端口级阻断，也可能是安全组没有放行。第三类，TCP 握手成功，但 TLS 握手失败或速度骤降，要怀疑 SNI 被识别、证书异常或线路限速。单次测试不能下结论。至少换两个国内运营商，间隔几分钟重复测试，避免把偶发丢包误判为被墙。

## 区分封锁、配置与网络问题的对比逻辑

对比时按“看到什么、判断什么、下一步做什么”推进，不要直接换 IP。
情况一：国内对入口执行 tcping 443 全部超时，境外同端口正常。判断为入口 IP 或端口被阻断，下一步先在服务端换一个端口验证。换端口后能通，说明是端口级封锁；仍不通，则倾向于整个 IP 被封。
情况二：国内外 tcping 都超时。判断与墙无关，下一步登录服务器，用 ss -tnlp 确认监听端口，再检查云厂商安全组和 iptables 或 nftables 规则。
情况三：端口可达，但客户端日志出现 tls handshake timeout 或 EOF。判断为 TLS 层问题，可能是 SNI 与证书不匹配，也可能是特征被识别。下一步用 openssl 检查握手。
情况四：只有部分用户、部分运营商异常。判断为局部线路质量问题或运营商策略差异，下一步用 mtr 观察丢包出现在哪一跳。

## 单节点排查步骤：DNS、SNI、TLS、客户端与服务端

1. 查 DNS。在国内执行 dig 节点域名，再与境外解析结果对比。如果国内返回的是异常 IP 或无响应，说明域名可能被污染，可以改用 IP 测试或更换解析方式。
2. 查 TCP。分别从国内和境外执行 tcping IP 端口，确认端口是否可达。
3. 查 TLS 与 SNI。执行 openssl s_client -connect IP:443 -servername 你的域名，确认证书链完整，证书域名与 SNI 一致。如果握手卡住，就换一个 SNI 再测，用来区分是证书问题还是特征识别。
4. 查服务端。执行 systemctl status xray，或用 journalctl -u xray -n 100 查看日志。注意是否有 failed to read、证书过期、配置解析失败等错误。
5. 查客户端。核对 UUID、传输方式、path、ALPN 是否与服务端一致，同时更新订阅，确认拿到的不是旧节点。
6. 记录结论。把每一步的结果按入口、端口、协议层分别记录，方便后续判断是单节点故障还是批量失效。

## 墙对比结果的覆盖验证：多地、多运营商、多时段交叉确认

单次墙对比只是一组样本，不能直接下结论。建议准备三类探测点：境外 VPS、国内电信、联通、移动各一个。每个点都执行同一组命令：nc -vz -w 5 节点IP 443 检查 TCP 握手；curl -v --resolve 你的域名:443:节点IP https://你的域名 检查 TLS；mtr -T -P 443 -c 20 节点IP 观察丢包出现在哪一跳。

判断逻辑可以按下面三种情况处理。境外正常、国内三网 TCP 全部超时，大概率是 IP 层封锁，下一步换入口 IP 并复测。国内 TCP 能连通，但 curl 停在 Client Hello 之后，或日志出现 connection reset，更像 SNI 或流量特征被干扰，下一步检查域名、证书和协议伪装配置。只有单个运营商异常，且 mtr 丢包集中在骨干跳，通常是线路或路由问题，下一步换中转或换线路。同一组测试要在白天和晚高峰各跑一次，避免把拥塞误判为封锁。

## 墙对比的失败边界：哪些情况下结论不可信

有几类情况会让墙对比失真。第一，探测点本身有问题，例如国内测试机所在机房出口异常，或者境外 VPS 被目标机房限速，这样测出来的是探测点的状态，不是节点的状态。第二，ICMP 不通不能说明被墙，很多服务商默认禁 ping，应以 TCP 和 TLS 的结果为准。第三，部分干扰是间歇性、端口级或只针对 UDP 的，短时间测试可能完全正常，需要拉长观察窗口，并对比客户端日志里的超时时间点。

第四，服务端防火墙、安全组、fail2ban 误封与被墙的表现很相似。区分方法是看境外是否也失败，以及服务端日志里有没有收到握手记录：境外也连不上，先查自身配置。第五，测试经过中转时，测到的只是入口，落地是否健康要单独在中转机上测。最后，换 IP 或换端口通常只能短期恢复。如果几天内同一位置再次失效，说明问题不在单个节点，继续轮换 IP 只会消耗资源。

## 长期架构与服务适用边界

当墙对比显示失效集中在入口层，长期思路是把入口、转发和后端解耦。入口只负责接入，可以低成本替换。中转负责线路选择和健康检查。落地源站不直接暴露公网 IP，只接受来自中转的流量。订阅端通过 XBoard/V2Board 下发分组节点，某个入口失效时，只需替换这一层，用户侧更新订阅即可恢复，不必迁移后端。配合多线路批量部署和定时的三网 TCP/TLS 探测，失效能更早被发现，切换也更有序。

## 常见问题

### 墙对比至少要测哪几项才算有参考价值？

建议至少测四项：ICMP ping、TCP 端口连通（如 nc -vz IP 443 或 tcping）、TLS 握手（openssl s_client -connect IP:443 -servername 你的SNI），以及客户端实际代理请求。只测 ping 不够，ping 通但 TCP 不通在封锁场景里很常见。

### 墙内 ping 通但端口不通，一定是被墙了吗？

不一定。先去墙外确认同一端口能不能连：墙外也不通，多半是防火墙、安全组或服务进程的问题；墙外通、墙内多个地区和运营商都不通，才更倾向于端口或 IP 被封锁。只有单一运营商失败时，还要考虑路由和丢包。

### 只能连一会儿就断，或者高峰期才断，算不算被墙？

这种情况更像 SNI 或协议特征被识别后的干扰，也可能是线路拥塞。可以按时段和地区多测几次墙对比，同时看服务端日志里有没有 reset、timeout、TLS handshake error，再结合不同线路的丢包率一起判断，不要只凭一次测试下结论。

### 换 IP 能解决问题吗？

短期内常常能恢复，但如果真正暴露的是源站、域名、SNI 特征或用户分布，新 IP 可能很快又失效。换 IP 后没几天就反复出问题，说明需要从入口、中转和落地的结构上处理，而不是只换地址。

## 总结

墙对比的核心是控制变量：同一节点、同一端口、同一 SNI，分别在墙内和墙外测 ICMP、TCP、TLS 和真实代理请求。墙外正常、墙内普遍失败，倾向于封锁；两边都失败，先查配置和服务端；只有局部失败，查线路。临时换 IP 或换端口只能缓解，如果问题反复出现，就要把入口、转发和后端拆开，并配上监控和切换方案。
