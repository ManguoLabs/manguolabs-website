# 内鬼如何解决：XBoard 订阅泄露的证据链排查与人工复核思路

关键词：内鬼如何解决、XBoard 订阅泄露排查、Token 多 IP 审计、账号关联追踪、订阅共享风险复核

内鬼如何解决，关键不在于先封谁，而在于先把证据链建起来：把 Token、注册 IP、登录 IP、订阅请求 IP、UA 和节点侧真实连接 IP 放在同一时间线上对比，再看历史关系和账号关联，最后由人工复核定性。单一 IP 重合只是线索，NAT、移动网络、多设备和代理都可能造成误判；风险概率可以排序，但不是封禁的唯一依据。

## 内鬼如何解决：先锁定证据链，再分级处置

XBoard 运营里说的“内鬼”，通常指把订阅链接转卖或分享给他人的账号，以及拿到订阅后批量导出节点、导致入口被针对性封锁的账号。解决的核心是先用证据确认是哪个账号、通过哪条订阅泄露、扩散到了哪里，再做重置 Token、限制设备或停用账号等分级处置。凭感觉整批封号会误伤正常用户，真正的泄露源头往往还留着。

可执行的顺序是：先把可疑时间窗内的订阅请求、登录记录和节点连接记录拉出来；再把同一个 Token 对应的 IP 与 UA 按时间排开；最后对照节点被封的时间点，找出在封锁前异常拉取订阅或首次连接的账号。风险概率只能作为排查优先级，不能当作封禁的唯一依据，处置前必须人工复核。

## 异常现象与证据清单：哪些信号值得深挖

常见的异常有几类。一是单个 Token 在短时间内被大量不同 IP 拉取订阅，UA 混杂 Clash、Shadowrocket、curl、python-requests 等多种客户端。二是新节点上线后很快被封，并且屡次发生，封锁前有少数账号异常频繁地刷新订阅。三是同一 IP 下出现多个新注册账号，注册时间集中，邮箱规律相近。四是节点侧连接 IP 的数量明显超出该套餐正常的设备规模。

建议在动手处置前整理一份证据清单：账号 ID 与邮箱、注册 IP 和时间、近 30 天登录 IP、订阅请求 IP 及 UA、节点侧真实连接 IP、节点上线时间与被封时间。截图要保留，原始日志也要保留。单条线索证明力很弱，比如“Token 出现 5 个 IP”可能只是用户在家、公司、手机之间切换。几类证据在时间上相互印证，才足以支撑判断。

## 按六类数据交叉排查的操作步骤

1. 从 Nginx 访问日志统计订阅请求，Token 用占位符代替：grep "client/subscribe?token=TOKEN_X" access.log | awk '{print $1}' | sort | uniq -c | sort -rn，得到这个 Token 的拉取 IP 和次数。
2. 加上 UA 字段再看一遍。看到 curl 或脚本类 UA 高频出现，说明可能有人在自动导出订阅，下一步要核对这个账号是否本人在用。
3. 用该账号的注册 IP 和登录 IP 去对比订阅 IP。三者长期不重合，订阅 IP 又分散在多个城市或运营商，转卖嫌疑就更高。
4. 拉取 Soga 节点侧的真实连接 IP，与订阅 IP 对照。只有订阅、没有连接，偏向导出节点；连接 IP 数量远超套餐设备数，偏向共享。
5. 把节点被封的时间对齐上面几条线索，筛出在封锁前首次连接或集中拉取的账号，列为优先复核对象。

## 处置后如何验证内鬼线索已被切断

处置不是终点，必须用数据确认泄露链路已经断开。建议按以下步骤验证：1. 对可疑账号执行订阅重置，记录重置时间点；2. 在 Nginx 访问日志中按旧 Token 检索，例如 grep "subscribe?token=旧值前8位" access.log | awk '{print $1}' | sort | uniq -c，观察旧 Token 是否仍被大量 IP 请求；3. 统计新 Token 在 24 至 72 小时内的请求来源，并与历史 IP 集合对比。

判断逻辑如下。如果旧 Token 持续被请求，但新 Token 只出现在原用户常用 IP 上，说明扩散端已被切断。如果新 Token 很快又出现在原来那批外部 IP 上，说明账号持有人仍在主动转发，需要进入人工复核。如果怀疑范围只能缩小到一组账号，可以给这组账号单独下发一个专用节点。该节点若被曝光或封锁，泄露源大概率就在这一组内。这种做法只能用来缩小范围，不能单独当作定性证据。

## 哪些情况下排查会失效或误判

第一类失效是"内鬼"本身有后台权限。员工、合作方或拥有数据库只读权限的人可以直接导出订阅链接或节点地址，重置用户 Token 对他们无效。这时应排查管理员登录日志、数据库账号授权和 API 调用来源。第二类是泄露内容根本不是订阅。对方可能截图节点 IP、端口和协议参数后手工配置，订阅日志里不会留下任何异常，只能依靠 Soga 等节点端记录的真实连接 IP 来比对。第三类是节点端证据失真。中转或负载均衡未开启 Proxy Protocol 时，节点只能看到中转机 IP，所有用户都会显示为同一来源。

另外，CGNAT、校园网、企业出口、移动网络切换基站、出差旅行、一人多设备，以及用户自己挂代理拉订阅，都可能产生"同 Token 多 IP"或"同 IP 多 Token"的表象。风险概率不是封禁唯一依据。先限速或要求用户说明，再结合历史关系决定是否封禁，能明显降低错封带来的客诉。

## 长期防内鬼的架构思路与服务适用边界

如果内鬼问题反复出现，靠手工 grep 日志很难持续跟进。长期方案应包含四个部分。一是把审计数据写入独立 MySQL，避免和 XBoard 主库争抢资源，也避免日志轮转后历史数据丢失。二是长期保存 Token、注册 IP、登录 IP、订阅 IP、UA 与真实连接 IP 之间的关系，让一次重置前后的变化可以前后对照。三是用仪表盘集中展示高风险账号和关联链路，方便运营人员复核。四是对后台人员实行最小权限，并保留操作审计记录。

## 常见问题

### 发现同一个 Token 出现在多个 IP 上，能直接认定是内鬼或订阅共享吗？

不能。同 Token 多 IP 可能来自手机切换 4G/5G 与 Wi-Fi、家庭与公司网络、旅行或使用代理更新订阅。应看 IP 是否跨地区同时活跃、UA 是否差异明显、节点侧真实连接 IP 是否与订阅 IP 对得上，并结合历史时间线判断，再交由人工复核。

### 同一个 IP 下有多个账号，说明这些账号是同一个人吗？

不一定。校园网、公司出口、运营商 CGNAT 和公共 Wi-Fi 会让大量无关用户共用出口 IP。需要叠加注册时间接近、UA 相同、邀请关系、支付或登录习惯等多维线索，并观察这种关系是否长期稳定，单一时间点的同 IP 只能作为弱信号。

### 为什么要保留长期历史关系，而不是只看最近几天日志？

内鬼通常会轮换 Token、换小号或间歇性分发，短期日志容易断链。长期保存 Token、账号与 IP 的历史关系，才能在重置订阅后继续追踪到旧关联，也能区分长期稳定的家庭 IP 与偶发的共享出口，减少误判。

### 账号关联追踪到第几层就应该停止？

层数越深，关联越弱、误伤越大。实践中可以把追踪上限设在有限层数（例如最多 8 层）用于调查视野，但处置通常只针对证据最充分的前一两层，深层账号更适合列入观察而不是直接处理。

### 风险评分很高的账号应该自动封禁吗？

不建议。风险概率只是排序和优先级工具，不是封禁的唯一依据。建议先人工核对原始日志与误判边界，必要时先重置订阅、限速或联系用户确认，再决定是否封禁，并保留处置记录以便申诉复查。

## 总结

解决内鬼问题的思路是：先收集异常现象与证据清单，再把 Token、注册/登录/订阅 IP、UA 与节点侧真实连接 IP 关联到同一时间线；利用长期历史关系解释同 Token 多 IP 与同 IP 多 Token，用有限层数的账号关联追踪定位源头；风险评分负责排序，人工复核负责定性，并始终考虑 NAT、共享网络、移动网络、旅行、多设备和代理造成的误判。少量账号可先用日志与 SQL 自查，长期、多账号的调查更适合用独立的审计系统持续沉淀证据。
